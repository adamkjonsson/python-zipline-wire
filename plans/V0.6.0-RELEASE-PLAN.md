# Plan: the `v0.6.0` release

**Written 2026-10-25.** `0.5.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. Eight issues sit on the `0.6.0`
milestone. Five were filed on 2026-10-24 from profiling `0.5.0`. Two are bugs
found reviewing `0.5.0` against python-zipline `0.7.0`. The last is the
pure-ACK question that spec `0.23` opened, held out of `0.5.0`.

| Issue | What it really is | In `0.6.0`? |
| --- | --- | --- |
| [#42](https://github.com/adamkjonsson/python-zipline-wire/issues/42) | **The dev venv runs sibling checkouts while reporting pinned versions.** Every measurement this release makes is only as good as knowing what it ran against | **Yes**: Phase 0, first |
| [#41](https://github.com/adamkjonsson/python-zipline-wire/issues/41) | The `zpf` pin has no upper bound. packeteer's has none either, and its minors break too | **Yes**: Phase 0, widened to packeteer (Decision 2) |
| [#44](https://github.com/adamkjonsson/python-zipline-wire/issues/44) | `_next_pending` is a linear `min`, so a drain is O(P²) | **Yes**: Phase 2 |
| [#43](https://github.com/adamkjonsson/python-zipline-wire/issues/43) | `_judge` scans all of `recent` on every timestamped repeat | **Yes**: Phase 2 |
| [#45](https://github.com/adamkjonsson/python-zipline-wire/issues/45) | `committed_gaps` is never pruned and is rescanned on every repeat. Carries an open question past 2 GiB | **Yes**: Phase 3 |
| [#47](https://github.com/adamkjonsson/python-zipline-wire/issues/47) | `describe_source` reads a stream-given capture whole into memory | **Yes**: Phase 4 |
| [#46](https://github.com/adamkjonsson/python-zipline-wire/issues/46) | Per-packet overhead on the in-order TCP path | **Yes, measure-gated**: Phase 4 (Decision 5) |
| [#37](https://github.com/adamkjonsson/python-zipline-wire/issues/37) | Store pure ACKs as zero-length records, now that spec `0.23` allows it | **Yes**: Phase 5, **on by default** and opt-out (Decision 1, taken 2026-10-25). The release's one **Breaking** change |

So `0.6.0` is **the performance release, and the pure-ACK release**. Phases
0–4 change no output: each must leave every byte of every conversion where
`0.5.0` put it. Phase 5 then moves the bytes of nearly every TCP conversion,
deliberately, and keeps `0.5.0`'s output one option away
(`pure_acks=False`, `--no-pure-acks`). The release also puts the dependency
pins and the dev venv on a footing where a "byte-identical" claim can be
believed. That is why those two bugs come first, though they are smaller
than the performance work.

## Where the tree stands

- **`main` is `0.5.0`** (`e292616`). Nothing has landed since.
- **Siblings.** Both have released since `0.5.0` was built:
  - python-zipline **`0.7.0`**. Spec `0.23` unchanged, with `zpf.open(...,
    check=False)` (python-zipline#97) and a 3.1× memory reduction in
    `packets_to_zpf` that this tree gets for free.
  - packeteer **`0.20.0`**. The internet checksum moved to C (packeteer#213,
    found by this tree), plus changes to stream generation that are breaking
    there and touch nothing here.
  - The sibling checkouts sit at those tags plus plan-only commits. The
    suite passes against them: **592 passed** (2026-10-25).
- **The venv is #42's trap, live.** `pip list` reports packeteer `0.19.0`
  and zpf `0.6.0`. The code it runs is `0.20.0` and `0.7.0`.

### Where the time goes

Measured 2026-10-25 on packeteer `0.20.0` and zpf `0.7.0`, CPython 3.14,
macOS arm64.

**On a clean capture** (`http_stream_1.pcap`, 4,140 packets) a conversion
takes **118 ms, about 35k packets/s**, against 149 ms on packeteer `0.19.0`.
Self time splits packeteer 33%, the zpf writer 22%, zpfwire 23%, and
built-ins 17%. Nothing dominates any more. zpfwire's in-order path is flat at
about 5 µs per packet.

**On hostile traffic** the reassembler's own data structures dominate. The
synthetic shapes are from the issues. *Prototype* is a monkeypatch of the
fix each issue proposes, which gave identical stats in every case and
byte-identical output on all 66 fixture × policy conversions:

| Issue | Shape | Now | Prototype |
| --- | --- | --- | --- |
| #43 | repeats carrying TSvals, 10 B segments | 212 µs/pkt | 7.6 (×28) |
| #43 | same, 100 B segments | 54 µs/pkt | 2.8 (×19) |
| #44 | reordered blocks of 2,000 × 100 B | 70 µs/pkt | 5.9 (×12) |
| #44 | reordered blocks of 170 × 1,460 B | 11.8 µs/pkt | 5.9 (×2) |
| #45 | 1 in 50 lost, 80k packets, window 4096 | 10.1 µs/pkt | 2.9 (×3.4) |
| — | in order, 1,460 B (control) | 5.3 µs/pkt | 5.2 |

The #43 prototype filed at ×76 now measures ×28. The difference is
`bisect` over a `deque`: CPython's deque is a linked list of blocks, so
indexing its middle walks the list. Bisecting 26,000 entries costs 2.7 µs on
a deque and 0.47 µs on a list. So the real fix wants `recent` list-backed
(Phase 2).

**Upstream.** The zpf writer costs about 10 µs per record whatever the
payload size: option encoding ~30%, the conformance checker ~22%, `Record`
validation ~17%, and `Flag`-enum arithmetic ~9%. Filed as
[python-zipline#101](https://github.com/adamkjonsson/python-zipline/issues/101)
on 2026-10-25. It is not on a python-zipline milestone, and this release does
not wait for it.

output, and in its speed.

this tree against the `v0.5.0` tag in a worktree, each with the same pinned

## Phase 2: the reorder buffer and `recent` (#44, #43)

**#44.** Beside `_Stream.pending`, keep the held sequence numbers in serial
order: offsets from an anchor, set to `next_seq` whenever the buffer goes
from empty to non-empty, held in a sorted list. Every held segment is ahead
of `next_seq` when `_hold` takes it, so the order is the serial order. The
next one is `order[0]`. `_hold` inserts with `bisect.insort`; `_release`
deletes with `bisect_left`. `_drain`, `_commit_gap` and `_commit_remaining`
are unchanged apart from calling `_next_pending`.

**#43.** `recent` becomes **list-backed**: a list and a head index, with
eviction advancing the head and compacting when the dead prefix is over
half the list. `_judge` bisects to the first entry whose end is past `seq`,
then walks forward until an entry starts at or past `end`. Entries are
visited in the order they are today, so the verdict, including which
fallback key is counted, cannot change. `bisect` with `key=` needs Python
3.10, which is the floor.

**Tests: equivalence against an oracle, not timing.** The old `_next_pending`
and `_judge` are copied into the test file as the reference, as packeteer
did for #213. Randomized streams, seeded and run under every policy, assert
that the new reassembler makes the same decisions call for call. The streams
mix reordering, repeats with and without TSvals, gaps, and sequence wrap.
The `_Stream` invariants (pending order, `recent` ascending and bounded) are
asserted after every packet in those streams.

- [ ] Byte-identity check: 198 of 198.
- [ ] The #44 and #43 rows of the benchmark within ×1.5 of the prototype or

- [ ] Control row unchanged within noise.

## Phase 3: committed gaps (#45)

**Settle the 2 GiB question first.** The issue suspects that, in a direction
longer than 2 GiB, a gap committed more than 2**31 bytes ago can look
*ahead* of a new segment under `_delta`, so today's full scan counts late
bytes against a gap they are nowhere near. That is cheap to test without
2 GiB of data. Commit a gap, then advance the stream by forward jumps, each
committing another gap and none further than `_MAX_WINDOW` (so
`splits_before` never fires). Once past 2**31, send a repeat that aliases
the first gap.

- **If it miscounts**, it is a bug: a *Fixed* entry. Because it moves bytes
  for that input, under `CLAUDE.md` it is also **Breaking**, limited to
  directions past 2 GiB that committed a gap. The test asserts the fixed
  answer, and the oracle in the equivalence test excludes that shape.
- **If it does not**, the test stays as a guard and the tail scan is a pure
  speed change.

**The fix.** Gaps are appended at `next_seq`, which only moves forward, so
`committed_gaps` is already ascending and its gaps don't overlap. Walk it
from the newest gap, stop at the first one wholly behind `seq`, and handle
what was collected in forward order. `_unclaimed`'s `sorted()` goes. Pruning
the list (dropping gaps more than `_MAX_WINDOW` behind) would bound memory
too, but it changes how a very late segment is classified, from late to
overlap. **Not done here**; noted under *What may still be filed*.

### Done when

- [ ] The 2 GiB test written, and its answer recorded below with the
  consequence it decided.
- [ ] Byte-identity check: 198 of 198.
- [ ] The #45 row within ×1.5 of the prototype or better.
- [ ] `CHANGELOG.md` *Changed*, with the numbers; plus *Fixed* and
  **Breaking** if the 2 GiB test found a bug.

## Phase 4: the small ones (#47, #46)

**#47.** `describe_source` hashes a stream in 1 MiB chunks, as it already
does a path, and restores the stream's position afterwards. A test feeds a
stream whose `read()` with no size raises, so a whole-file read fails the
test. *Fixed* in the changelog. The digest is unchanged.

**#46, gated on the benchmark** (Decision 5). Each item is tried alone
against the control row, and kept only if it moves the control row or the
clean-capture conversion by **5% or more**:

1. Trackers derive the sender endpoint from `self.key` instead of formatting
   it (`TcpFlow.packet`, `UdpFlow.packet`).
2. `slots=True` on `_Contribution`, `_Sent`, `_Gap` and `_Pending`.
3. One `zpf.Decoded` per `CaptureSink`, not one per record.
4. A 256-entry flag table in `_write` in place of the `_FLAG_MAP` loop.
5. `_stamp` and `_commit_remaining` pass the three fields `_append` reads
   rather than building a `PacketView`.

Whatever is not kept is listed on #46 with its measurement, and #46 closes
at release with that comment. A kept item gets a *Changed* line only if
the gain is worth stating; otherwise it is an internal refactor and needs
no entry.

## Phase 5: pure ACKs, stored by default (#37)

By Decision 1, a pure ACK is stored unless the caller opts out. This is a
**Breaking** change to what a conversion writes, and the only one in the
release.

- **`ReassemblyOptions.pure_acks: bool = True`.** CLI `--no-pure-acks`, in
  the style of `--no-coalesce` (`pure_acks=not args.no_pure_acks`), a
  one-liner in `__main__.py`. `packets_to_zpf` takes it through `options`
  like every other policy field, so the two conversions stay aligned.
- **`params_digest` names the field only when it is `True`.** Today it
  hashes `asdict(self)` whole, so any new field would move every file's
  Decoder descriptor, including files written with the option off. The
  digest therefore drops `pure_acks` when it is `False`. A
  `pure_acks=False` conversion then declares the same `params_digest` as
  `0.5.0`, writes the same bytes, and the reproducibility contract still
  tells the two policies apart. A test pins both properties: the digest
  with the option off equals `0.5.0`'s, and it differs with the option on.
- **A pure ACK is a zero-length record** at the sender's `next_seq` with its
  `ack` hint, no flags beyond what it carried, and the packet as its only
  origin. On a `.zpf` input it is then cited, not left to `skipped`.
- **Placement, the phase's one design question.** A zero-length record
  sits at a stream offset like any other, and records are stored in
  ascending `seq_start`. A pure ACK arriving while its sender has an open
  run sits at that run's end, so it cannot be written before the run.
  There are two ways round it:
  - **Flush the run at the pure ACK.** Simple, but it ends a coalesced run
    where today it would not, so record boundaries move with the option on.
  - **Hold the pure ACK and write it after the run closes.** Boundaries are
    unchanged, but a held ACK's `ts` then precedes the run's, so whether
    that breaks a `ts` rule needs checking against the spec.

  Prototype both; the docs state the one chosen and why. With the option
  on by default, the stakes are higher than they would be for an opt-in:
  flushing would change record boundaries for every default conversion,
  not only for the callers who asked. So holding is preferred unless the
  spec check rules it out. Under `favor-acked` a stored pure ACK still drives
  `_settle` as it does today; only its storage is new.
- **Docs**: the coalesced-`ack` rule (#11) restated for a file holding both
  (the data record's `ack` is what was true when it completed; a pure ACK's
  is a separate observation at its own time).
- **Measure the cost, and publish it.** A bulk transfer has about one pure
  ACK per two data segments, and each costs a ~10 µs writer call
  (python-zipline#101). By default, then, a conversion writes roughly half
  as many records again, and some of the time Phases 2–4 save goes to
  writing them. The benchmark gains `http_stream_1.pcap` rows with the
  option on and off, plus file sizes, and the release section quotes both,
  so nobody reads "the performance release" and finds the default slower.
- **The pins.** `test_pins.py` pins the sixteen pre-Timestamps fixtures at
  the `0.2.0` decode, and that decode must stay reachable. Those pins run
  with `pure_acks=False` and keep their digests. A second pinned set
  records the new default's decode of the same sixteen, so the default's
  output is pinned as firmly as the old one.
- **The rest of the suite.** Tests that count records, compare a `.zpf`
  input's sessions with its capture's (`test_packets.py`'s differential),
  or check the `skipped` regions of a `.zpf` input assume pure ACKs are not
  stored. Each is updated to the new default, or pinned to
  `pure_acks=False` where what it tests is not about pure ACKs. Which one
  is a per-test call, made in review, not in bulk.
- **Tests of the feature.**
  - `--sequenced` over every fixture reads clean and merges. This
    exercises spec `0.23`'s no-edge rule, which nothing here has relied on
    before.
  - A `.zpf` input cites its pure ACKs and marks nothing `skipped` for them.
  - A one-way upload (a peer sending only pure ACKs) gets the tighter merge
    #37 promises.
  - The byte-identity check with `pure_acks=False` still passes 198 of 198
    against `v0.5.0`.

- [ ] `params_digest` unchanged from `0.5.0` with the option off, and

## Decisions

### 1. #37: store pure ACKs by default, with an opt-out — **taken 2026-10-25**

#37 offered three options: always store, an opt-in, or never. The decision
is a fourth, between the first two: **store by default, and let a caller
opt out.** #37 stays on the milestone.

What it buys is what #37 argued for, now for every caller who doesn't ask
otherwise: tighter causal ordering under `--sequenced`, the receiver's
reaction times in the file, and a cited rather than `skipped` packet on a
`.zpf` input. What it costs:

- **A Breaking release.** The bytes of nearly every TCP conversion move.
  Below 1.0 that is allowed in a minor, and it is called out (Phase 6).
- **Records and time.** Roughly half as many records again on a bulk
  transfer, each a writer call. Measured and published (Phase 5).
- **The placement question** (Phase 5) affects every default conversion.

The opt-out is what makes it safe to ship. With `pure_acks=False`, a
conversion is `0.5.0`'s, down to the Decoder's `params_digest`. Anyone
reproducing an existing file has one switch to flip, and the byte-identity
check keeps meaning what it meant in Phases 2–4.

### 2. Bound both siblings to one minor — **recommended**

#41 proposes `zpf<0.8`, leaving the floor open. Recommended:

- **`zpf>=0.7.0,<0.8`.** One minor wide, so the range is the one release the
  suite runs against. `0.7.0` writes the same spec as `0.6.0`, so moving the
  floor costs no user anything, and it lets a future change use `check=`
  without a second floor move.
- **`packeteer>=0.16.0,<0.21`**, which #41 does not ask for. packeteer's
  changelog says the same thing about its minors that python-zipline's does,
  and `0.20.0` carried two **Breaking** entries. Neither touches this tree,
  which is luck, not a promise. The floor stays where the suite needs it
  (`0.16.0`, for the generated `favor-acked` test); the code itself needs
  nothing newer.

Each bound needs widening, deliberately, at each sibling release. That is
the point.

### 3. Two venvs, not one — **recommended, as #42 proposes**

Co-developing against the checkouts stays possible (`.venv-dev`), but stops
being the default. The pytest header makes a stale install visible either
way. The alternative, one venv with a loud header, was rejected: the header
is read when someone thinks to look, and the 2026-10-24 review only
produced numbers worth publishing because it did not trust `.venv`.

### 4. A benchmark script, not timing tests — **recommended**

Timing assertions in pytest are flaky on shared machines and CI, and a
generous threshold proves little. Correctness is pinned by equivalence
tests against an oracle (Phases 2–3). Speed is a checked-in script whose
numbers each phase records. If a regression guard is ever wanted, an
operation count (calls to `_delta` per packet on a fixed stream) is
deterministic and could be asserted. Not in this release.

### 5. #46 is measure-gated at 5% — **recommended**

The in-order path is flat and its cost is spread out. Each #46 item is a
little more code, or a little less obvious code, for a little speed. 5% of
the control row or of a clean conversion is the bar at which a change is
worth its diff. Below it, the measurement is recorded and the item dropped.

## Sequencing and risk

Phase 0 first, so every later number says what it ran against. Phase 1
before any fix, so a fix is measured against the tree it changes. Phases 2
and 3 are the release; Phase 3 starts with a test that may turn a speed
change into a bug fix, so it is not merged with Phase 2. Phase 4 is small
and can slip. Phase 5 is last because it is the only phase allowed to move
output: Phases 2–4 are each proved against `0.5.0` with nothing else
moving, and Phase 5 is proved against them with the option off. Phase 5 is
also the largest and the one with an open design question, so if the
release must shrink, Phase 4 goes first, not Phase 5. The risks:

- **A fix that changes a verdict.** The fixtures barely reach the hot paths,
  so the byte-identity check alone is weak evidence for #43–#45. The
  oracle tests are what carry it, and they need shapes the fixtures lack:
  deep reorder, small segments, TSvals on repeats, and wrap.
- **The 2 GiB answer.** If Phase 3's test finds a miscount, `0.6.0` gains
  a **Breaking** line it did not plan. It is narrow, limited to directions
  past 2 GiB that committed a gap, and has to be named in the changelog,
  not buried.
- **Sibling releases mid-flight.** With the bounds in place, a zpf `0.8.0`
  or packeteer `0.21.0` during this release does not reach users, but does
  reach `.venv-dev`. Re-run the suite in `.venv` before tagging.
- **The default's cost.** If Phase 5 measures storing pure ACKs as costing
  more than Phases 2–4 save on a clean capture, the release section says so
  plainly. python-zipline#101 is then the fix that matters most for this
  tree, and its priority there is worth raising, with the numbers.
- **Hidden assumptions about pure ACKs in the suite.** Phase 5's suite pass
  is a per-test review, and it is where the time goes. A test bulk-switched
  to `pure_acks=False` to make it green would hide exactly what the phase is
  meant to show.
- **python-zipline#101 lands first.** Welcome, but it would need zpf
  `0.8.0`, which is outside this release's bound. It is a `0.7.x` patch or
  the next release's step, not this one.

**Sizing.** Phase 0, half a day. Phase 1, half a day. Phase 2, a day. Phase
3, a day, half of it the 2 GiB test. Phase 4, half a day. Phase 5, about three
days: one for the feature and the placement question, one for the
suite's review, half each for the pins and the docs. Phase 6, half a day.
**About seven days.**
