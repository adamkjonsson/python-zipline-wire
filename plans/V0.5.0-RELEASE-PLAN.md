# Plan: the `v0.5.0` release

**Written 2026-10-13.** `0.4.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. Four issues sit on the `0.5.0`
milestone. Three are the carry-overs `0.4.0` filed in its Phase 4. The
fourth, #35, is new and much larger than the other three together: it is
the first time this project reads a `.zpf` instead of a capture.

| [#30](https://github.com/adamkjonsson/python-zipline-wire/issues/30) | The generated `favor-acked` test, which wants the packeteer floor at `0.16.0` | **Yes**: Phases 0 and 1. This is the packeteer step the issue said to wait for |
| [#31](https://github.com/adamkjonsson/python-zipline-wire/issues/31) | The fifth site: a superseded held segment never sets `retransmit`. By decision, or by inheritance? | **Yes**: Phase 2. Measured below: no fixture reaches the site |
| [#32](https://github.com/adamkjonsson/python-zipline-wire/issues/32) | A dedicated bound for the `favor-acked` hold, *if a capture ever needs one* | **No work.** Phase 5 re-checks the condition and takes it off the milestone (Decision 5) |

So `0.5.0` is **the `.zpf`-input release**. It is the first release whose
headline is a capability rather than a spec port or a reassembly rule. It is
also the first in which this tree is a *derived-file* producer, which brings
in rules it has never had to keep: the coverage guarantee, `input_extents`,
the no-splice duty, and `zpf-input` provenance.

### What a real `packets.zpf` looks like

#35 describes its input from `vectors/tunnel/packets.jsonl`. That vector is
synthetic: its payloads are `PPPP…`, not IP, so nothing can parse them. The
shape that matters is what zipline-kober actually writes. This was generated
by running kober's own chain test
(`test_generated_impaired_traffic_decodes_to_exactly_what_arrived`: packeteer
→ `wg_seal.py` → `zpfwire convert` → `kober run --emit field`) and reading
the output back:

```
session 0  proto=udp  key="198.51.100.7:51820 <-> 203.0.113.9:51820"
  pid 0  adjacency=units      pid 1  adjacency=units
records: 181   prim:u32 62, prim:u8 50, prim:bytes 36, dec:ip-packet 33
undecoded: skipped 9, decrypt-failed 9  (all naming outer.zpf)
discontinuity: none
session_end input_extents: pid 0 → 2608, pid 1 → 2720
diagnostics: []  unplaceable: []
```

It differs from the vector in five ways, and each one changes the design:

1. **The packets are interleaved with field records.** Each WireGuard field
   (`type`, `reserved`, `receiver`, `counter`, the handshake bodies) is a
   record of its own, and only 33 of 181 are `dec:ip-packet`. Selecting by
   `content_type` is therefore required, not a convenience. Every other
   record's range still has to be accounted for under the coverage
   guarantee, as `skipped`.
2. **Both directions, one participant each.** Inner packets come from two
   input streams, and kober stores one direction's records before the
   other's. Stored order is *not* time order across participants, so the
   reader has to merge by `ts`.
3. **`adjacency = units`, not `contiguous`.** Every seam of the input is a
   declared break. Under the spec's no-splice duty, an output unit whose
   `spans` cross two input units needs either a `units` output participant
   or a Discontinuity. A transport-layer output can have neither, so a
   record here **must not cite two input packets** (Decision 3). The tree
   coalesces TCP segments into runs today, so this is a real constraint.
4. **A failed decryption is not a Discontinuity.** It is a bytes-class
   `decrypt-failed` region naming `outer.zpf`, a file that is not our input.
   The issue's question, "carry the input's reason forward?", has no carrier
   on this shape. On the vector's shape, the carrier is a widthless
   Discontinuity, which has no range to name. See Decision 2.
5. **Padding past the IP datagram stays in the record.** A sample record is
   64 bytes with `total_length` 57. packeteer's `parse_packet(…,
   link_type=LINKTYPE_RAW, decode_app=False)` trims the extra bytes, and the
   UDP payload comes out at 29 bytes. That was checked on the generated file.

The packeteer pieces all exist and are public: `parse_packet` with
`LINKTYPE_RAW`, `Defragmenter(link_type=LINKTYPE_RAW).feed(frame, ts,
token=…)` for inner fragments, and `write_pcap(…, link_type=LINKTYPE_RAW)`
for the export. The private `_packet_from_records` that `iter_packets` uses
is three lines on top of `parse_packet`, so no packeteer shim is needed.
`write_pcap` iterates its input once and works with a generator (tested),
so an export streams. Only its annotation says `list[PacketTuple]`:
[packeteer#204](https://github.com/adamkjonsson/packeteer/issues/204).

### #31, measured

The issue's first step is "count the shape". `TcpFlow._release` was
instrumented to count entries into the superseded-held branch at
[`tcp.py:592`](../src/zpfwire/tcp.py#L592), and all 22 fixtures were swept
under both overlap policies:

```
_discard calls across the sweep: 113        superseded-held branch entered: 0
```

**No fixture reaches the fifth site, under either policy.** The issue's
first objection ("the pins move") is moot. The change is a `0.3.0`-style
rule with a synthetic test, and its **Breaking** entry is stated for a shape
no fixture has, as `0.3.0` did for PAWS.

The second objection ("the covering run may already be written") **does not
hold either, read against the code.** `_drain` is reached from `_accept`
right after the fill is appended ([`:512`](../src/zpfwire/tcp.py#L512)) and
from `_commit_gap`, which flushes *before* it drains
([`:698`](../src/zpfwire/tcp.py#L698)). `_append` never flushes, and the
flush in `packet()` runs only after `_accept` returns. So whatever covers
the superseded held segment was appended in the same call and is in the open
`stream.run`. A held segment sits past the hole, so its start is at or past
the run's `seq_start`. "Flag when the covering run is open" is therefore
always, not "when it can". Phase 2 turns that reading into an `assert` and a
test.

## Phase 3: a `.zpf` of IP packets becomes sessions (#35) — **TODO**

The headline. It is written here as the order of work. Decisions 1–4 shape
it, and the first of them has to be taken before the second box is ticked.

### The seam: a second reader beside `CaptureReader`

- [ ] **`PacketView` learns where it came from in an input `.zpf`.** Today
  `payload_offset: int | None` is a capture byte offset, and every discard
  site's arithmetic (`_cite(payload_offset, skip, length)`) assumes one.
  Add an `origin` carrying the packet's input locator: the `(session_id,
  pid)` of the input stream and the `[off_start, off_end)` of each input
  record the packet came from (more than one for a defragmented datagram).
  Under Decision 2's whole-packet granularity, a contribution cites its
  packet's ranges and the arithmetic is not used. `payload_offset` keeps its
  meaning for capture inputs. **No byte of a capture conversion may move**:
  the 44 digests are this phase's regression guard, and they are checked
  after the refactor, before any new code reads the field.
- [ ] **`PacketRecordReader`** (name to argue with) in a new
  `src/zpfwire/packets.py`. It opens the input with `zpf.open`, selects
  records by `content_type` (default `dec:ip-packet`), merges the selected
  records of every input participant by `ts` (stable on input session, pid
  and stored index), defragments with
  `Defragmenter(link_type=LINKTYPE_RAW)`, parses with `parse_packet(…,
  link_type=LINKTYPE_RAW, decode_app=False)`, and yields `PacketView`s.
  Ticks are the input's `tick_hz`. It keeps the same `skipped` tally and
  `SkipReason` keys `CaptureReader` uses, plus whatever is new
  (`content-type-not-selected` is counted in records, not packets, and
  reported separately). `CaptureReader` and it satisfy one `Protocol` that
  `convert()` takes.
- [ ] Memory: the `ts` merge across participants needs either independent
  per-participant iterators from `zpf`'s reader or materialising the
  selected records. Measure what `FileReader` offers. If it is
  materialising, say so in `limits.md`, and record it as a python-zipline
  ask under #76 rather than shimming it.

### The writer side: a derived file, transport layer

Depending on Decision 1, this is either `zpf.sessionize_stage`
(python-zipline#76) or the primitive API under a `SHIM — python-zipline#76`
comment. The obligations are the same either way, and they are what the
tests check:

- [ ] **Source and Decoder.** One `zpf-input` Source with the input's `uri`
  and `sha256` digest (`describe_source` already hashes). The same
  `DECODER_NAME` with `output_layer = TRANSPORT` and `params_digest()`.
  `produced_by` and `produced_at` are required, since a derived file's
  checker enforces them. `produced_at=None` must therefore be refused or
  mapped, not passed: decide in the phase. Pinning it to an `int` still
  works for reproducibility.
- [ ] **Spans on every record.** Each record's `Decoded(decoder=…,
  spans=…)` cites, per Decision 2, the input range of every packet that fed
  it, adjacent ranges merged. Zero-length records (the SYN record, a FIN
  attached to an empty run) cite their packet too.
- [ ] **Coverage, per input participant stream, across all output
  sessions.** Every byte of every input stream is cited by a span or named
  by an Undecoded block, and never both:
  - records not selected (kober's field records): `skipped`, adjacent ranges
    merged into one block;
  - packets that feed no record (pure ACKs, a retransmitted SYN, non-TCP/UDP
    such as ICMP, packets of a transport not asked for or filtered out by
    `--proto`/`--port`/`--host`): `skipped`. They carry no content of a
    stream this file produces, which is what keeps them from being
    `dropped` (see Decision 2);
  - a packet discarded whole by reassembly: its existing reason
    (`duplicate-discarded`, `overlap-discarded`, `late-*`, `paws-rejected`,
    `bad-checksum`), now against the `zpf-input` source with real
    `session_id`/`pid`;
  - a packet that does not parse as IP: `undecodable`;
  - an inner datagram whose fragments never completed: each fragment's
    record, `undecodable` with `comment` saying why.
- [ ] **`input_extents` on every Session End.** Each output session declares
  the *whole* extent of every input stream it cited, which is the fan-out
  rule. The input is a file in hand, not a live decode, so extents come
  from the reader up front (`zpf.stream_extent` per input participant).
- [ ] **Never cross an input seam that does not join** (Decision 3). A run
  closes before a packet whose input record does not join the previous
  contributor's: every seam in a `units` participant, and a Discontinuity
  in a `contiguous` one. On kober's input that means one record per TCP
  segment, which is the price of the rule until the zipline issue below is
  answered. Coalescing is unchanged for capture inputs.
- [ ] **No Discontinuity is ever written.** The output is transport layer,
  and the spec forbids one there. The input's breaks show up as holes in
  the sequence numbers, exactly as the vector's `inner.zpf` shows them.

## Phase 4: decrypted packets out as a pcap (#35, the comment) — **TODO**

The issue's own text argues *against* a pcap round trip, because it cuts
the provenance chain. The comment asks for one anyway, for a different
reason: Wireshark. Both are right. This is an **export for analysis**, not a
step in the chain, and the docs say that plainly.

- [ ] **`zpfwire.packets_to_pcap(source, sink, *, content_type="dec:ip-packet",
  packet_filter=None)`**, sharing Phase 3's reader for selection and the
  `ts` merge, so the two functions select the same packets. Its signature is
  aligned with `packets_to_zpf`. It writes `LINKTYPE_RAW` (101), which
  carries IPv4 and IPv6 alike. Nanosecond pcap when the input's `tick_hz`
  needs it, microsecond otherwise, rescaled the way
  `CaptureReader._ticks` rescales.
- [ ] **Bytes exactly as the record holds them.** Kober's padding stays,
  and Wireshark shows it as a trailer. An export that edits what it exports
  needs a reason, and none has been given.
- [ ] Fragments are written as the fragments they are. Wireshark
  reassembles them, and defragmenting in the export would be a second
  interpretation.
- [ ] CLI: a subcommand, `zpfwire pcap INPUT.zpf -o OUT.pcap
  [--content-type …] [filters]`. It is a new verb and not a `convert` flag,
  because it produces a different kind of file. Or `export`: settle the
  name when the CLI page is written, and keep it short.
- [ ] Tests: export the differential helper's `packets.zpf` and compare
  against the source capture's IP layer with packeteer's reader: same
  packets, same order, same timestamps. If `tshark` is on `PATH`, one
  smoke test opens the file, skipped otherwise, as kober's suite does.
- [ ] Pass `write_pcap` a generator. It streams already; until
  [packeteer#204](https://github.com/adamkjonsson/packeteer/issues/204)
  widens the annotation, that one call needs a `cast` with a comment naming
  the issue, which is deleted when the fix lands.
- [x] Split from #35 as its own issue:
  [#36](https://github.com/adamkjonsson/python-zipline-wire/issues/36), on

## Decisions

### 1. python-zipline#76: wait for it, or shim it? — **open; recommendation: shim**

#35's writer side is exactly what #76 describes: fresh output sessions,
records citing an input stream, coverage unioned across output sessions,
`input_extents` under fan-out, input seams honoured. `DecodeStage` mirrors
sessions 1:1, so it cannot be used. #76 is on python-zipline `0.6.0`, which
was put on hold today until spec `0.23`.

- **Wait.** This is upstream-first in its purest form, and zpfwire would be
  #76's first consumer, which is the best test its API could get. But
  `0.5.0` would then have no date, and kober's Stage 5, which decided today
  to wait for #35, would wait on a spec release too.
- **Shim.** Write the stage on the primitive API (`add_source(ZPF_INPUT)`,
  `begin_session`, `record(decoded=Decoded(spans=…))`, `undecoded`,
  `end(input_extents=…)`, all present in `0.5.0`), with the coverage and
  extent bookkeeping in one module behind a `SHIM — python-zipline#76`
  comment. Shape its interface like #76's sketch, so the swap is a
  deletion. Post on #76 what this stage turned out to need: `sequenced` and
  `linearize` sessions, `Hints`, `ts_first`, flags, multi-range cites per
  record, `units`-input seams. That makes the shim the pressure test.
- **Or un-hold #76.** python-zipline's own plan says #76 "touches none of
  the ordering code" and needs no spec change. Shipping it as `0.5.3` or a
  fan-out-only `0.6.0` reverses a decision taken today, which is yours to
  make, not this plan's.

**Recommendation: shim**, because it unblocks kober and is the cheapest way
to find out what #76's API must be. It is temporary by `CLAUDE.md`'s rule
and is deleted in the release that consumes #76.

### 2. What a span cites: the whole packet, or only the payload bytes — **open; recommendation: whole packet**

The issue raises it. The vector's `inner.zpf` cites the whole 60-byte
packet for a 40-byte payload. The spec's test is *correspondence, not
proximity*: "whether the bytes fed the unit". The IP and TCP headers fed
the unit, because they are what placed the bytes in the stream.

- **Whole packet** (the vector's choice). A record cites every packet that
  contributed to it. Undecoded blocks exist only for packets that
  contributed *nothing*. Partial overlaps are not visible in the file, since
  the packet is cited and "never both" forbids also naming part of it. The
  stats still count them. Fewer blocks, and the existing `_cite` arithmetic
  is not needed on this path.
- **Payload bytes only.** Spans are exact, and every discard site's
  existing arithmetic carries over with `payload_offset = record offset +
  header length`. But every packet's headers then need a `skipped` block,
  roughly one Undecoded per packet, and the file says less about what fed
  the record, not more.

**Recommendation: whole packet.** It matches the vector, it is the spec's
own reading for a stage that consumes framing, and it keeps the file small.

On carrying `decrypt-failed` forward: there is nothing to carry it in. A
transport stream may not hold a Discontinuity. The input's break is either
widthless (the vector: no range to name) or a region of `outer.zpf` (kober:
not our input). The chain stays walkable: an inner sequence hole falls
between records whose spans cite packets either side of the input's break.
**Decided by the format, not by preference.** The guide page says so.

### 3. The no-splice duty on a transport-layer output — **conservative now, zipline issue for the rule**

Filed as [zipline#152](https://github.com/adamkjonsson/zipline/issues/152).
Read literally, the spec forbids this stage from coalescing two packets of
a `units` input into one record. That forbids exactly what a TCP reassembler
is for, and its sequence numbers are themselves the evidence that the two
join. The spec's text ("no third case is defined") was written with a
decoded output in mind, and a transport output can declare neither `units`
nor a Discontinuity. **Implement the conservative reading**: runs close at
every input seam that does not join, so kober's input gives one record per
segment. **Ask the spec** whether a transport-layer output's anchored
offsets discharge the duty (zipline#152). If zipline says yes, the
cut goes and records coalesce again. That would move bytes, and the
changelog entry would say so then.

### 4. No dependency on packeteer `0.18.0` — **taken**

Kober's chain needs `0.18.0`'s `tunnel_stream` to generate traffic. This
suite does not: the differential helper builds `packets.zpf` from the 22
captures already here, which also gives #35 real TCP (retransmits,
Timestamps, wraps, fragments) that a DNS-over-WireGuard corpus would not.
The floor moves to `0.16.0` for #30 and no further.

### 5. #32 stays open, off the milestone — **taken, pending Phase 5's measurement**

Its own close condition has not fired, and nothing in this release
supplies the capture it waits for. It was milestoned when the milestone was
opened, not because `0.5.0` could answer it.

### 6. Input selection is not in `params_digest` — **taken**

`--content-type` changes the output, as `--port` already does, and neither
is hashed: `params_digest()` covers the reassembly policy, and a new field
there would move the descriptor on every file (#32's reasoning). Follow the
filter precedent. The selection is still stated in the file (the Source
`comment`, or the File Header's) so a reader can see it. Whether this
tree's *input selection* belongs in the reproducibility contract at all is
a fair question. It predates this release, so it gets an issue in this repo
if anyone wants it answered.

## Sequencing and risk

Phases 0 → 1 → 2 are small and touch the reassembler first, so the digest
baseline is settled before Phase 3 refactors `PacketView` under it. Phase 3
is most of the release. Phase 4 builds on Phase 3's reader. 5 and 6 are
mechanics. The risks:

- **The `payload_offset` → `origin` refactor moving a capture byte.** Run
  the 44 digests after the refactor and before any feature code. This is
  the one regression that would ship unnoticed, since every capture test
  would still read clean.
- **Coverage is new to this tree.** A capture source discharges no
  coverage obligation, so the tree has never had to account for every input
  byte. The packets that feed no record are the easy ones to miss: pure
  ACKs, a SYN retransmission, a FIN-only segment whose flag attaches to an
  existing run. The checker in the tests is the guard. Run it on every
  variant of every fixture, not a sample.
- **Withholding from a UDP stream.** The spec says a transport-layer stage
  "MUST NOT withhold content from a stream whose offsets are not
  sequence-anchored". `--checksum drop` on an inner UDP datagram does that,
  and so it does on a capture today. That is pre-existing and not this
  release's to settle. But #35 makes it concrete, because kober's corrupted
  datagrams arrive as exactly this. Read the clause against `_drop` in
  Phase 3, and file in this repo or ask zipline, whichever it turns out to
  be.
- **`dec:ip-packet` is a decoder-private token.** `dec:` tokens are scoped
  to the decoder's `name`: the vector's is `wireguard-decrypt` and kober's
  is `wireguard`. A generic sessionizer matching the bare token is trusting
  a convention, not the format. Both producers in existence agree, so the
  default is fine. The format question is
  [zipline#153](https://github.com/adamkjonsson/zipline/issues/153).
- **A defragmented inner datagram on a `units` input** cites several input
  units by construction, and under Decision 3 cannot. Tunnels set inner
  MTUs, so this should be rare. Do not build per-fragment record splitting
  for it: refuse it with an `undecodable` per fragment record and a counter,
  and let the zipline answer to Decision 3 settle it.
