# Plan: the `v0.5.0` release

**Written 2026-10-13; revised 2026-10-15 against the python-zipline `0.6.0`
release candidate.** `0.4.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. Four issues sat on the `0.5.0`
milestone when this plan was written. Three were the carry-overs `0.4.0`
filed in its Phase 4. The fourth, #35, is new and larger than the other
three together: it is the first time this project reads a `.zpf` instead of
a capture. #36 was split from it since.

So `0.5.0` is **the `.zpf`-input release, on spec `0.23`**. It is the first
release whose headline is a capability rather than a spec port or a
reassembly rule. It is also the first in which this tree is a
*derived-file* producer, which brings in rules it has never had to keep:
the coverage guarantee, `input_extents`, the no-splice duty, and
`zpf-input` provenance. Since spec `0.22`, most of those are kept for us by
`zpf.sessionize_stage`.

## What this revision changed

The first draft (2026-10-13) was written against python-zipline `0.5.2` and
spec `0.21`. Five of its open questions were answered upstream in two days.
zipline released **`0.22` and `0.23`** on 2026-10-14, and python-zipline cut
a **`0.6.0` release candidate** implementing `0.23`, with
`sessionize_stage` (python-zipline#76) in it. On 2026-10-15 it was decided
that **`0.5.0` is built against that RC**. Anything this work finds in
python-zipline is filed for its `0.6.0` milestone and fixed on that branch,
not shimmed here. `0.5.0` is tagged only once python-zipline `0.6.0` is
final.

## What a real `packets.zpf` looks like

#35 describes its input from `vectors/tunnel/packets.jsonl`. When the issue
was written that vector was synthetic, and it is real packets only since
`0.22`. The shape that matters most is what zipline-kober actually writes.
This was generated on 2026-10-13 by running kober's own chain test
(`test_generated_impaired_traffic_decodes_to_exactly_what_arrived`:
packeteer → `wg_seal.py` → `zpfwire convert` → `kober run --emit field`)
and reading the output back:

```
session 0  proto=udp  key="198.51.100.7:51820 <-> 203.0.113.9:51820"
  pid 0  adjacency=units      pid 1  adjacency=units
records: 181   prim:u32 62, prim:u8 50, prim:bytes 36, dec:ip-packet 33
undecoded: skipped 9, decrypt-failed 9  (all naming outer.zpf)
discontinuity: none
session_end input_extents: pid 0 → 2608, pid 1 → 2720
diagnostics: []  unplaceable: []
```

It differs from the vector in five ways. What each one means since `0.22`:

1. **The packets are interleaved with field records.** Each WireGuard field
   is a record of its own, and only 33 of 181 are packets. Selecting by
   `content_type` is required. The stage's auto-fill marks every unselected
   range `skipped` on close. **kober labels its packets `dec:ip-packet`**,
   not `net:ip`, so until kober moves to the format's label a user passes
   `--content-type dec:ip-packet` (Decision 7).
2. **Both directions, one participant each.** kober stores one direction's
   records before the other's, so stored order is not time order across
   participants. The reader merges by `ts` (streaming; see Phase 3).
3. **`adjacency = units`.** Every seam of the input is a declared break.
   Under `0.21` that forbade coalescing; **since `0.22` it does not**, for a
   record that carries `seq_start`. A UDP record carries none, and a UDP
   datagram is one record of one packet anyway. The exception is a
   fragmented one (zipline#166, *Sequencing and risk*).
4. **A failed decryption is not a Discontinuity.** It is a bytes-class
   `decrypt-failed` region naming `outer.zpf`, a file that is not our input.
   There is nothing to carry it forward in (Decision 2).
5. **Padding past the IP datagram stays in the record.** A sample record is
   64 bytes with `total_length` 57. packeteer's `parse_packet(…,
   link_type=LINKTYPE_RAW, decode_app=False)` trims it, and the UDP payload
   comes out at 29 bytes.

The packeteer pieces are all public: `parse_packet` for either link type,
`Defragmenter(link_type=…).feed(frame, ts, token=…)` for inner fragments,
and `write_pcap` for the export, which takes any iterable since
packeteer#204.

## #31, measured

The issue's first step is "count the shape". `TcpFlow._release` was
instrumented to count entries into the superseded-held branch at
[`tcp.py:592`](../src/zpfwire/tcp.py#L592), and all 22 fixtures were swept
under both overlap policies:

```
_discard calls across the sweep: 113        superseded-held branch entered: 0
```

**No fixture reaches the fifth site, under either policy.** The issue's
first objection ("the pins move") is moot. The change is a `0.3.0`-style
rule with a synthetic test, and its **Breaking** entry is stated for a shape
no fixture has, as `0.3.0` did for PAWS.

The second objection ("the covering run may already be written") **does not
hold either, read against the code.** `_drain` is reached from `_accept`
right after the fill is appended ([`:512`](../src/zpfwire/tcp.py#L512)) and
from `_commit_gap`, which flushes *before* it drains
([`:698`](../src/zpfwire/tcp.py#L698)). `_append` never flushes, and the
flush in `packet()` runs only after `_accept` returns. So whatever covers
the superseded held segment was appended in the same call and is in the open
`stream.run`. A held segment sits past the hole, so its start is at or past
the run's `seq_start`. "Flag when the covering run is open" is therefore
always, not "when it can". Phase 2 turns that reading into an `assert` and a
test.

## Phase 3: a `.zpf` of IP packets becomes sessions (#35) — **TODO**

The headline, built on `zpf.sessionize_stage`. The stage owns the Source,
the Decoder at the transport layer, coverage per input stream across every
output session, auto-fill, and whole-stream `input_extents` on every
Session End. This tree owns what the stage deliberately does not: parsing
packets, flows, reassembly policy, and the reasons for what it discards.

### Upstream first: what the RC must gain

Both go to python-zipline's `0.6.0` milestone, asked before filed, and are
fixed on its branch. Neither is shimmed here.

- [ ] **A new session on an ended key**, [python-zipline#88](https://github.com/adamkjonsson/python-zipline/issues/88), filed
  2026-10-15 for `0.6.0`. `SessionizeStage.session(key)`
  caches by key and returns the *ended* session for a key used before, even
  with an explicit `session_id`, and writing to it raises `ZpfError`
  (probed 2026-10-15 on `7bbc44e`). This tree opens a second session on the
  same key in two places: a flow that **times out** and resumes, and a
  **`capture-gap`** split, where spec §*Referencing the source by stream
  offset* says the producer "ends the session at the hole and opens another
  on the same key". Neither can go through the stage today. Until it is
  fixed, those two paths over a `.zpf` input are strict `xfail`s naming
  python-zipline#88. Everything else in this phase is unaffected.
- [ ] **`face`** (and `creator`) on `sessionize_stage`, [python-zipline#89](https://github.com/adamkjonsson/python-zipline/issues/89),
  filed 2026-10-15 for `0.6.0`. It calls
  `zpf.create` with neither, so its output is binary only and the File
  Header has no `creator`. `capture_to_zpf(face="jsonl")` and `--jsonl`
  have no equivalent for a `.zpf` input. This is smaller: until it lands,
  `--jsonl` with a `.zpf` input is refused with a message naming the issue,
  and the differential test lists `creator` as a stated difference.

### The seam: one tracker, two sinks

- [ ] **The trackers write through a sink, not a `SessionWriter`.**
  `FlowTracker` calls `session.participant`, `session.record(…, decoded=…)`
  and `cite_undecoded` against the capture today. Introduce a small sink
  with those three operations and two implementations. *Capture*:
  `SessionWriter` plus `Decoded(decoder=…)`, and Undecoded at capture byte
  offsets, which is today's code moved. *Packets*: `FlowSession.participant`,
  `FlowSession.record(…, cites=…, ts=…, ts_first=…)`, and
  `SessionizeStage.undecoded(stream, …)`. `_begin` and `_close` in
  `convert.py` go through the sink, so `convert()` stays one loop over
  either input. **No byte of a capture conversion may move**: the 88-file
  comparison is this refactor's guard, run after it and before any new
  code reads the new fields.
- [ ] **`PacketView` learns where it came from in an input `.zpf`.** Today
  `payload_offset: int | None` is a capture byte offset. Add an `origin`:
  the input `Span`s of every record the packet came from (`stream.cite(…)`
  over each `Datagram`, more than one for a defragmented datagram), and the
  input stream they name. `_Contribution`, `_Pending` and `_Alternate` carry
  it beside `payload_offset`. A run's record cites the union of its
  contributors' origins (Decision 2, whole packets), adjacent ranges merged.
- [ ] **`ts`, `ts_first` and `ack` stay this tree's.** `_hints(run)` already
  computes all three from the contributors, excluding a copy displaced
  under `favor-acked`. They are passed explicitly, never derived by the
  stage, whose derivation counts every *cited* input record, a displaced
  copy's included (*What was filed for this plan*, #86).

### The reader

- [ ] **`PacketRecordReader`** (name to argue with) in a new
  `src/zpfwire/packets.py`, over `stage.streams()`.
  `heapq.merge` of each stream's `datagrams()` by `(ts, stream index,
  off_start)`. The views are lazy and may be interleaved, so the merge
  streams and memory stays bounded by the reassembler, not the input. It
  selects records whose `dg.record.content_type` matches the selection
  (Decision 7), defragments with `Defragmenter(link_type=…)`, parses with
  `parse_packet(…, link_type=…, decode_app=False)`, and yields
  `PacketView`s in the input's `tick_hz`. Same `SkipReason` keys as
  `CaptureReader`. `CaptureReader` and it satisfy one `Protocol` that
  `convert()` takes.

### What the file says about every input byte

The stage auto-fills every input range nothing cited or marked as
`skipped`, so this tree writes **only** the regions it has a reason for. It
must never cite and mark the same range: the stage raises at close.

- [ ] **Cited**: every packet that contributed a byte or a flag to a record,
  whole (Decision 2). That includes a packet only partly kept (an overlap
  trimmed, a `favor-acked` loser), the SYN behind the SYN record, and a FIN
  whose flag attaches to a run.
- [ ] **Marked, with this tree's reason** (bytes class, as on a capture): a
  packet discarded whole by reassembly (`duplicate-discarded`,
  `overlap-discarded`, `late-*`, `paws-rejected`, `bad-checksum`), against
  the input stream with its real `session_id`/`pid`. A selected record that
  does not parse as IP or Ethernet, and the fragments of a datagram that
  never completed, are marked `undecodable` with a `comment`.
- [ ] **Left to auto-fill (`skipped`)**: records not selected (kober's field
  records), pure ACKs (Decision 8), non-TCP/UDP packets, a transport not
  asked for, and packets the filters exclude. They carry no content of a
  stream this file produces, which is what keeps them from being `dropped`.
- [ ] **No Discontinuity is ever written.** The output is transport layer.
  The input's breaks show up as holes in the sequence numbers, as in the
  vector's `inner.zpf`.

## Decisions

### 1. Build on `sessionize_stage`, against the python-zipline `0.6.0` RC — **taken 2026-10-15**

The first draft weighed waiting for python-zipline#76 against shimming it,
and recommended the shim. The question went away: python-zipline cut a
`0.6.0` RC with the stage in it, and it was reviewed from here and found
sufficient once #86 (`ts_first`) was fixed on its branch. So `0.5.0` builds
on the RC. What this work finds in python-zipline is filed for its `0.6.0`
milestone and fixed there, never shimmed here. The cost is the release gate
in Phase 6: `0.5.0` waits for `0.6.0` to be tagged, and re-measures on the
tag before it claims it.

### 2. A span cites the whole packet — **recommended, and the vector agrees**

The spec's test is *correspondence, not proximity*: "whether the bytes fed
the unit". The IP and TCP headers fed the unit, because they are what
placed its bytes in the stream. `0.22`'s re-vendored `tunnel` does the
same: `inner.zpf`'s first record carries 40 bytes and cites the whole
80-byte packet `[0, 80)`.

- **Whole packet.** A record cites every packet that contributed to it.
  Undecoded blocks exist only for packets that contributed *nothing*.
  Partial overlaps are not visible in the file, since the packet is cited
  and "never both" forbids also naming part of it. The stats still count
  them.
- **Payload bytes only.** The spans would be exact. But every packet's
  headers would then need a `skipped` block, roughly one Undecoded per
  packet, and the file would say less about what fed the record, not more.

On carrying `decrypt-failed` forward: there is nothing to carry it in. A
transport stream may not hold a Discontinuity. The input's break is either
widthless (the vector, which has no range to name) or a region of
`outer.zpf` (kober, not our input). The chain stays walkable: an inner
sequence hole falls between records whose spans cite packets either side
of the input's break. **Decided by the format.**

### 3. Records coalesce over a `.zpf` input as over a capture — **resolved by zipline `0.22` (#152)**

The first draft read the no-splice duty literally: a transport output
could not cite two units of a `units` input, so every run would be cut at
every seam. zipline#152 was filed, and `0.22` answered it: "a
transport-layer output whose records carry `seq_start` meets both duties
through its offsets" and MAY cross input units or an input Discontinuity.
So nothing is cut, and the differential test compares record boundaries
too. A transport output **without** sequence numbers still owes both
duties. That leaves one shape with no conformant record, a fragmented UDP
datagram over a unit sequence, which is
[zipline#166](https://github.com/adamkjonsson/zipline/issues/166).

### 4. No dependency on packeteer `0.18.0` — **taken**

Kober's chain needs `0.18.0`'s `tunnel_stream` to generate traffic. This
suite does not: the differential helper builds `packets.zpf` from the 22
captures already here, which also gives #35 real TCP (retransmits,
Timestamps, wraps, fragments) that a DNS-over-WireGuard corpus would not.
The floor moves to `0.16.0` for #30 and no further.

### 5. #32 stays open, off the milestone — **taken, pending Phase 5's measurement**

Its own close condition has not fired, and nothing in this release
supplies the capture it waits for.

### 6. Input selection is not in `params_digest` — **taken**

`--content-type` changes the output, as `--port` already does, and neither
is hashed: `params_digest()` covers the reassembly policy, and a new field
there would move the descriptor on every file (#32's reasoning). Follow the
filter precedent, and state the selection in the File Header's `comment` so
a reader can see it.

### 7. Select `net:` by default; parse by the label's link type — **taken 2026-10-15**

Since `0.22` a packet-preserving stage labels its records `net:ip` or
`net:ethernet`, and those labels mean what `LINKTYPE_RAW` and
`LINKTYPE_ETHERNET` mean, whichever decoder wrote them. So the default
selection is **both `net:` labels**, each parsed with its own link type
from `zpf.NET_LINK_TYPES`. `--content-type` selects a different label
instead, such as kober's current `dec:ip-packet`, and `--link-type` says how
to parse it (default `LINKTYPE_RAW`). This is python-zipline's
recommendation for this project, and it is what the format now says a
generic consumer matches.

### 8. Pure ACKs are not stored in `0.5.0` — **taken**

Spec `0.23` makes storing them safe, and #37 asks whether to. That is a
change to what every TCP conversion writes, a **Breaking** entry of its
own. Inside #35 it would make the differential test measure two changes at
once. On a `.zpf` input, a pure ACK's packet is left to auto-fill as
`skipped`, which is conformant. #37 is decided on its own terms, later.

## Sequencing and risk

Phase 0 first, because it turns the suite green. Phases 1 and 2 touch the
reassembler while every capture still converts to the same bytes. Phase 3
is most of the release, and its upstream items are filed at its start, so
python-zipline has the whole phase to land them. Phase 4 builds on Phase 3's
reader. Phases 5 and 6 are mechanics. The risks:

- **The RC moves under us.** It is a branch, not a tag. Re-run the 88-file
  comparison and the suite whenever `../python-zipline` is pulled, and read
  python-zipline's changelog diff rather than assume.
- **The sink refactor moving a capture byte.** Run the 88-file comparison
  after it and before any feature code. This is the one regression that
  would ship unnoticed, since every capture test would still read clean.
- **Cite-and-mark collisions.** The stage raises at close if a range is both
  cited and marked. A packet partly kept is cited and never marked. Getting
  that wrong fails loudly, which is the right way round, but every variant
  of every fixture has to run to find it.
- **Withholding from a UDP stream.** The spec says a transport-layer stage
  "MUST NOT withhold content from a stream whose offsets are not
  sequence-anchored". `--checksum drop` on a UDP datagram does that, on a
  capture as much as on a `.zpf`. #35 makes it concrete, because kober's
  corrupted datagrams arrive as exactly this. Read the clause against
  `_drop` in Phase 3, and file in this repo or ask zipline, whichever it
  turns out to be.
- **Fragmented UDP over a unit sequence** has no conformant record until
  zipline#166 is answered. It is marked `undecodable` per fragment and
  counted. Tunnels set inner MTUs, so it should be rare. Do not split the
  datagram into several records for it: a UDP record is a `message`.
- **The release date is python-zipline's.** If `0.6.0` slips, so does
  `0.5.0`. kober's Stage 5 can verify against the `0.5.0.dev` build before
  then, which is what it is waiting for.
