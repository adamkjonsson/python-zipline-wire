# Plan: the `v0.8.0` release

**Written 2026-10-27.** `0.7.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. The work is tracked by three
issues on the [`0.8.0` milestone](https://github.com/adamkjonsson/python-zipline-wire/milestone/8):

| Issue | What |
| --- | --- |
| [#64](https://github.com/adamkjonsson/python-zipline-wire/issues/64) | Fidelity for UDP: delivery, duplication and order of datagrams |
| [#63](https://github.com/adamkjonsson/python-zipline-wire/issues/63) | A public `zpfwire.fidelity` and a `zpfwire fidelity` subcommand |
| [#67](https://github.com/adamkjonsson/python-zipline-wire/issues/67) | Both siblings' names are taken on PyPI (dependency confusion) |

`0.8.0` is **the UDP counterpart of `0.7.0`**. `0.7.0` built an instrument
that scores a TCP conversion against what packeteer sent, and fixed what it
found. This release points the same instrument at UDP (#64). It then decides
whether the TCP metrics have earned a public API (#63). #67 is not about
fidelity. It goes first because it changes how every venv in this plan is
built.

## Which project, and which version

**zpfwire `0.8.0`**, against spec `0.23`, python-zipline `0.7.0` and
packeteer `0.21.0`. Nothing in this plan needs a sibling release.
packeteer `v0.21.0` already has everything UDP needs: two-way `messages`
(packeteer#195) and `reorder_probability` both exist at the tag, not only on
`main`. A minor bump, because #67 narrows the dependency declaration
(Phase 1) and #63 adds public API.

## Where the tree stands

- **`main` is `0.7.0`** (`08d292e`), and nothing has landed since.
- **The siblings** are python-zipline `0.7.0` (spec `0.23`) and packeteer
  `0.21.0`, pinned by tag in `requirements.txt` and declared as ranges in
  `pyproject.toml`. The packeteer checkout is two commits past its tag, both
  of them plan-only.
- **The last fidelity sweep** is `0.7.0`'s, `summary.md` sha256
  `ce1fe4a9777e68a45f139bd24735d3ff2a2ea324f84562d58aface936dc757af`.
  Phase 2 reproduces it before it moves anything.
- **zpfwire's UDP path is small.** `UdpFlow` (`src/zpfwire/udp.py`, 54
  lines) writes one `message` record per datagram, in capture order, with no
  `seq_start`. Both checksum policies keep a corrupt datagram and count it
  (`0.5.0`). On the packets path (`.zpf` input), a fragmented datagram is
  marked `undecodable` and counted under `SKIP_FRAGMENTED_UDP`, since
  [zipline#166](https://github.com/adamkjonsson/zipline/issues/166) leaves no
  conformant record for it. That issue is open.
- **The spec forbids withholding UDP content.** A transport-layer stage
  **MUST NOT withhold content** from a stream whose offsets are not
  sequence-anchored (§Discontinuity, *Conformance*). A datagram left out
  leaves no trace, and no reader can check. That rule decides most of what a
  UDP scorer should expect. It is the one thing in zpfwire's UDP path that a
  reader can never verify, so this tool verifies it.

### What the prototype found

The prototype was run on 2026-10-27, in `.venv`, against the pinned
releases. It used 40 datagrams alternating c2s and s2c, sizes 100–1,399
bytes, position-unique payloads, and seeds 0–9: 400 datagrams per cell. It
generated with `generate_udp_stream(config=UDPStreamConfig(messages=…,
impairments=…))` and converted through both paths: `capture_to_zpf`, and
`packets_to_zpf` on a `.zpf` of the same packets (`tests/helpers.py`'s
`packets_zpf`). Every file read back clean.

| Impairment | What the network did | Capture path | Packets path |
| --- | --- | --- | --- |
| none | — | every datagram written once, exact | same |
| loss 0.1 | 41 lost | the other 359 written once | same |
| duplication 0.2 | 77 copies captured | **77 copies written** | same |
| reorder 0.2 | 57 out of send order | all written once, **57 inversions** | same |
| corruption 0.2 | 77 corrupt | 77 written corrupt, under `ignore` **and** `drop` | same |
| MTU 576, none | 240 of 400 fragmented | all written | **240 withheld**, cited `undecodable` (580 fragment regions) |

Four things in that table shape the plan:

- **The capture path conserves every captured datagram exactly.** Nothing is
  lost, invented or moved. That is the expected result: `UdpFlow` makes no
  choices. So the main risk this time is the opposite of `0.7.0`'s. A scorer
  that is satisfied too easily would report a perfect UDP path whether or not
  it is one. Every *Done when* below includes a mutation that has to fail.
- **A captured copy is written as a second record, and must be.** TCP
  discards a capture-point copy and cites it as `duplicate-discarded`. For
  UDP, the withholding rule forbids that, and nothing in the format can mark
  a kept record as a copy of another. A reader of the file sees the message
  twice. That is a question for the format, not a zpfwire defect (Phase 6).
- **Reordering cannot be undone.** A datagram carries no sequence number, so
  stored order is arrival order. The spec names capture order as the rule.
  Each inversion is information the capture never held, and the scorer
  explains it rather than counting it as a failure (Decision 4).
- **The packets path withholds every fragmented datagram.** It cites each
  one, so accounting holds, but the bytes are missing from the stream. That
  is zipline#166, now measured: 60% of datagrams at this scenario's sizes and
  a 576-byte MTU.

## Phase 3: the UDP truth and ledger — **DONE** (2026-10-27)

Built from the generator alone, as for TCP. Nothing in this phase reads a
`.zpf`.

**The truth** is the list of datagrams each application sent: direction,
index, bytes and true send time. Payloads are position-unique per datagram:
the first 16-byte block identifies (direction, index), and every later block
is keyed by its position. A record can then be traced to its datagram by its
first block, even when corruption has flipped its last byte. The minimum
size is 16 bytes. Empty datagrams get a scenario of their own, since a
zero-length datagram is a record (`test_an_empty_datagram_is_still_a_record`).
`num_data_packets` is pinned to `len(messages)`, and `base_time` to
`BASE_TIME`, for the reasons Phase 1 of `0.7.0` found.

**The ledger** has one entry per captured packet: datagram index, label
kinds (`DATA`, `DUP`, `REORDER`, `CORRUPT`, `FRAG`, outermost first), capture
time, and whether its checksum verifies. Two things are derived from it:

- **Lost datagrams** are the indices no packet carries. packeteer drops a
  lost datagram before anything else happens, and a lost datagram has no
  further consequence.
- **Realised reorders** are what the scorer explains inversions by. Each
  `REORDER` entry counts how many datagrams going its own way overtook it.

**Self-checks**, which void a run:

- every `CORRUPT` datagram fails its UDP checksum. An IPv4 checksum of 0
  means "none", and would make a corruption invisible, so that case must be
  caught;
- every `DATA`, `DUP` and `REORDER` payload equals the truth for its index;
- a `DUP` is byte-identical to the packet it copies, apart from the capture
  time;
- a fragmented datagram's fragments reassemble to the truth (or to its
  corrupted copy).

### Done when

- [x] A scenario turns into a truth and a ledger. Tests cover a clean flow,
  each impairment alone, all of them at once, and fragmentation.
- [x] **Shown to fail**: a hand-damaged ledger (a `CORRUPT` with a valid

### What Phase 3 execution changed

- **`tools/fidelity_udp.py`** mirrors the TCP module: `Impairments`,
  `Scenario`, `Truth`, `Ledger`, `self_check`, `Run` and `run`. Its
  `PROTOTYPE` is the prototype's 40 datagrams. The server is `10.0.0.2:5000`.
  **`tests/test_fidelity_udp.py`** has 293 tests and one strict xfail, and
  runs in under 2 s.
- **The ledger's unit is a captured copy, not a packet.** A `Copy` is one
  datagram as the capture holds it. Its frames are grouped by packeteer's
  label with the `FRAG[…][i]` around a fragment taken off, and reassembled
  by fragment offset. Two copies of one datagram always differ in label,
  since the second is `DUP[…]`. A copy keeps:
  - its payload;
  - its first and last frame times;
  - its **pieces**, where each run of payload bytes sits in which frame.
    Phase 4 locates citations with them.
- **The ledger computes the UDP checksum itself**, over the IPv4
  pseudo-header. packeteer cannot verify a fragment's checksum, since the
  UDP header travels in the first fragment only. A test holds the ledger's
  verdict equal to packeteer's on every whole datagram.
- **The send time is a formula**: datagram *i* is sent at `BASE_TIME` +
  (*i*+1) ms, packeteer's gap with no jitter. A self-check holds every
  `DATA` copy's first frame to it.
- **`overtaken`** counts, for each copy, the later datagrams going its way
  that the capture completed first. It is not bounded by `reorder_depth`:
  packeteer counts only datagrams delivered in turn toward a held one's
  wait, so another held datagram released earlier overtakes it as well.
  Only `REORDER` copies are overtaken when reordering is the only
  impairment, which a test holds over 40 seeds.
- **Self-checks**:
  - a copy travels its datagram's way;
  - a copy is corrupt exactly when its checksum fails, and a corrupt copy
    differs from the truth in its last byte only;
  - every other copy carries the truth;
  - a `DATA` copy was first captured at its send time;
  - a `DUP` matches the copy it duplicates.

  **None fires on any of 480 runs**: 40 seeds × 6 impairment sets
  (none, each alone, all at once) × whole and fragmented. Four tests damage
  a ledger by hand, and each voids the run with exactly the expected line.
  A corrupt empty datagram has its checksum's byte flipped, so no payload
  changes, and that case is tested too.
- **A packeteer defect, found here: a fragmented flow does not reproduce
  from its seed.** packeteer builds every datagram with IP ID 0, and
  `fragment_ipv4` replaces a zero ID with a draw from Python's *unseeded*
  global `random`. Two runs of one seed then differ in the fragments' ID and
  IP checksum, though `UDPStreamConfig.seed` promises byte-identical output.
  It is also why a duplicated fragmented datagram carries a fresh ID, where
  a capture-point copy would repeat the same fragments. Related: the
  datagrams are sent with DF set, and the middlebox fragments them anyway.
  The ledger does not depend on IDs, so no run is affected. The reproduction
  test's fragmented case is a strict xfail naming it. Filed, after asking,
  as [packeteer#232](https://github.com/adamkjonsson/packeteer/issues/232),
  covering all three. Phase 5 has to show the sweep's report is still
  deterministic, since IP IDs never reach a `.zpf` record.
- **Output unchanged**: 198 of 198 identical to `v0.7.0`; 1,227 tests.

## Phase 4: the UDP scorer — **DONE** (2026-10-27)

The conversion runs through both paths, the capture path and the packets
path. The packets path needs a `.zpf` of packets, so `tests/helpers.py`'s
`packets_zpf` moves to `tools/` and the tests import it from there
(`pythonpath` already has `"tools"`).

**Delivery**, per sent datagram. Let *c* be how many times the capture holds
it and *w* how many records carry it:

| Class | Condition |
| --- | --- |
| **conserved** | *w* = *c* ≥ 1, each record's bytes equal to a captured copy |
| **lost** | *c* = 0, *w* = 0: the network's |
| **withheld** | *w* < *c*: zpfwire's, and a withholding-rule question unless cited |
| **invented** | *w* > *c* |
| **altered** | a record's bytes match no captured copy |

These give two scores, mirroring `0.7.0`'s pair:

- **delivery**: datagrams written exactly once with their true bytes ÷ sent.
  That is what a reader of the file gets. Duplication lowers it, as does
  corruption.
- **conservation**: conserved ÷ captured, which is what zpfwire made of what
  it was given. It should be 1 wherever no citation explains a shortfall.

**Accounting**:

- every captured datagram not in a record is cited by an `Undecoded`
  block: by multiplicity, as for TCP, so a datagram both written and cited
  is caught;
- `stats.records`, `stats.payload_bytes` and `stats.bad_checksum` agree with
  the ledger;
- every record carries `message`, and none carries `retransmit`. A UDP
  sender never resends here, and the flag names the sender's act;
- the session count is one per flow and the end reason is `capture-end`,
  unless the scenario provokes a timeout.

**Order**:

- **per direction**: stored order against send order. Each inversion is
  attributed to a realised `REORDER`. An inversion that no ledger entry
  explains is a failure;
- **across directions**: `session.timeline()` against capture order. zpfwire
  has no reason to depart from it, so any difference is a failure. Send
  order across directions is not scored. packeteer sends a reply whether or
  not its request arrived, so no causal dependency exists to check.

**Timing**: each record's `timestamp` should equal its packet's capture time
exactly, in ticks. For a fragmented datagram the phase records which
fragment's time zpfwire takes, and pins it. Against the *send* time, a
reordered datagram is late by the time it was held, and that is reported,
not scored.

  one record removed reports *withheld*; one written twice reports
  *invented*; one citation removed reports a datagram lost quietly; two
  records swapped in a JSONL file report an unexplained inversion; and one
  timestamp moved by a tick is caught.

### What Phase 4 execution changed

- **The scorer is in `tools/fidelity_udp.py`**: `convert`, `read`, `match`,
  `score` and `measure`, which return `Delivery`, `Accounting` and
  `OrderScore`. The module is 1,194 lines. `tests/test_fidelity_udp.py` has
  728 tests and one strict xfail, and runs in 5 s. 1,662 tests in all.
- **Records are matched to copies by bytes, in order**, not by the first
  block. Per direction, each record in stored order takes the earliest
  unclaimed copy, in capture order, with exactly its bytes. That works for
  any size, empty datagrams included. A copy's two records are told apart
  by order, which is what the order checks then judge. So the 16-byte
  minimum the plan set is not needed.
- **The packets path writes its own `.zpf` of packets** (`packets_of`),
  from the stream, rather than moving `tests/helpers.py`'s `packets_zpf`.
  The scorer has to know where each frame lands in the input's offset space
  to locate citations, and the test helper's options (field records,
  interleaving) serve other tests. Its shape is the helper's default: one
  `net:ip` record per frame, one participant per direction, capture order.
- **Citations are located per path.**
  - On the capture path, a citation names capture-file bytes, and a copy's
    payload is located by its pieces.
  - On the packets path, a citation names an input participant's offsets
    (`participant_id`, `off_start`, `off_end`), and covers frames whole.

  A copy is *cited* when all of it is covered. A partly covered copy, or a
  copy both written and cited, is a failure.
- **Provenance is checked where it exists.** A packets-path record's spans
  must name exactly its copy's frames. Capture-path records carry no spans.
- **Timing, pinned:** a fragmented datagram's record carries its *last*
  fragment's capture time, when the datagram was complete. Every record's
  `timestamp` must equal its copy's completion time to the microsecond.
- **`sequenced` is TCP-only in zpfwire** (`convert.py`), so on UDP it
  should change nothing. Phase 5 runs it as a policy to check that.
- **Order is counted as pairs**, not adjacent drops. The prototype's "57
  inversions" counted descents; the scorer counts pairs out of send order,
  135 over the same 400 datagrams. Each is explained by the later-stored
  copy carrying `REORDER`. **Misordered**, records out of their copies'
  capture order, is the failure; none occurs.
- **The prototype's table reproduces** through the scorer, on both paths,
  pinned as a test. On the capture path every impairment and both
  checksum policies give conservation 1. On the packets path at MTU 576,
  240 fragmented datagrams are withheld and all 240 cited (zipline#166).
  **No accounting failure on any run**, on either path.
- **Shown to fail**, each by a test that replaces part of a real
  conversion's output and rescores it:

  | Mutation | Caught as |
  | --- | --- |
  | a record removed | `quiet` 1, and conservation below 1 |
  | a record written twice | `invented` 1 |
  | a record's bytes reversed | `unknown` 1, and its copy `quiet` |
  | two records swapped | `misordered` 1, `unexplained` 1 |
  | a timestamp moved by 1 µs | `mistimed` 1 |
  | a packets-path citation removed | `partial` 1 |
  | a span moved by a byte | `misattributed` 1 |

  Two differ from the plan. The swap edits the read-back output rather than
  a JSONL file, since UDP conversion takes no `face` here and the scorer
  only sees the output. A removed citation shows as *partial*, not *quiet*:
  the packets path cites each fragment separately, so removing one leaves
  the datagram partly cited.
- **Output unchanged**: no `src/` change; 198 of 198 identical to `v0.7.0`.

## Phase 5: the sweep, and a UDP baseline

The matrix gains UDP families. The TCP rows of `summary.md` must stay
byte-identical to Phase 2's.

- **Families:**
  - request/response, the prototype's 40 datagrams;
  - one-way bulk, 2,000 datagrams near the MTU;
  - small datagrams (16–64 bytes), so the 16-byte identity block is tight;
  - large datagrams fragmented at MTU 576 (`mtu=`);
  - empty and one-byte datagrams.
- **Impairments:** none; loss at 0.02 and 0.1; duplication at 0.05 and 0.2;
  reorder at 0.05 and 0.2 with depth 3, and 0.2 with depth 10; corruption at
  0.2; all of them at once.
- **Policies:** the default; `checksum=drop`; `sequenced`; a short
  `session_timeout` against a scenario with a pause in it. Each runs on both
  paths. A UDP cell does not run a TCP-only option, since it would only
  repeat the default.
- **Realised, not configured**, and **deterministic**, as in `0.7.0`: cells
  exercised fewer than 10 times are marked as such, and two sweeps with
  different `--jobs` give identical reports.

The baseline goes into this plan, as `0.7.0`'s did, with its sha256.

## Phase 6: triage

## Phase 7: a public `zpfwire.fidelity` (#63)

#63 set its own condition: the metrics should have **survived a release
unchanged**. This phase checks the condition first. Its gate: no TCP
scoring definition has changed since `v0.7.0`, which means Phase 2's
byte-identical sweep, and no later phase touching `fidelity_tcp.py`'s
scoring. If the gate fails, #63 is carried over again, and the release goes
out without it.

The answers to #63's four questions:

- **Which metrics are promised.** Fidelity, recovery, attribution and
  accounting (`ByteScore`, `Accounting`) become public. Order and timing
  stay in `tools/`, as the issue itself suspected they should. Phase 3 of
  `0.7.0` changed the order score twice. **UDP stays in `tools/` for this
  release** (Decision 3).
- **packeteer is already a runtime dependency.** `zpfwire.capture` imports
  it, and the generator ships in the same distribution, so no extra is
  needed. The cost is import time. `zpfwire/__init__.py` does not import
  `zpfwire.fidelity`, so `import zpfwire` pays nothing for it, and a test
  holds that.
- **Scenarios as configuration.** The public `Scenario` and `Impairments`
  are frozen dataclasses. The CLI describes one scenario with flags:
  - messages as `--messages c2s:3000,s2c:9000`;
  - impairment flags named as packeteer's own CLI names them
    (`--loss`, `--duplicate`, `--retransmit-lost`, …);
  - the reassembly flags `convert` takes, through the same argparse group,
    so `--overlap favor-acked` means the same in both;
  - `--seeds N`.

  A scenario file format is deferred. TOML would need `tomli` on 3.10, and
  nothing yet asks for one.
- **The report** keeps both Markdown and JSON Lines, deterministic byte for
  byte, and Markdown goes to stdout. `__main__.py` only parses arguments and
  prints. A function in `zpfwire.fidelity` builds the report.

What lands where:

- `src/zpfwire/fidelity/`, lifted from Phase 2's `fidelity_common.py` and
  `fidelity_tcp.py`;
- `tools/fidelity.py` keeps the project's matrix and the multiprocessing
  sweep, built on the public module;
- the tests split along the same line.

The signatures are drawn so that a UDP scenario can be added in `0.9.0`
without a break: `measure(scenario, options)` dispatches on the scenario's
type.

## Decisions

### 1. `pyproject.toml` alone names the sibling tags: **recommended**

#67 proposes keeping the tags in both `pyproject.toml` and
`requirements.txt`, with a test that the two agree. Once `pyproject.toml`
holds exact URL references, `requirements.txt`'s lines add nothing:
`pip install -e .` installs the same tags, and a second copy is something
to keep in step. So `requirements.txt` keeps the development tools only.
The alternative, both copies plus an agreement test, is safe too, and costs
one more edit at each sibling release.

### 2. Split the tool before adding UDP: **recommended**

Adding UDP to a 1,941-line TCP module would mix the two. Splitting the tool
first, with a byte-identical sweep as the check, means the UDP work cannot
move a TCP number unnoticed. It is also the shape #63 needs.

### 3. TCP public, UDP still a tool: **recommended**

#63's rule is the one `0.7.0` Decision 2 set: metrics in their first release
carry no promise. The UDP metrics are new in this release, so they wait one
release, and their API is added in `0.9.0` without a break. The
alternative is to make both transports public now, so that one release
delivers the whole UDP counterpart. That breaks the rule #63 was filed
under, and any change to a UDP definition in `0.9.0` would then be a
**Breaking** entry.

### 4. Reordering and duplication are reported, not failed: **recommended**

A UDP stream has no anchors. Writing a reordered datagram where it arrived,
and a captured copy as a record, is what the spec requires of a
transport-layer stage. The scorer explains each against the ledger. What it
fails is anything the ledger does not explain: an inversion without a
`REORDER`, or a copy written more or fewer times than it was captured.

### 5. SCTP stays out

packeteer refuses every impairment on SCTP, as #64 notes. There is nothing
to measure.

## Format notes

Nothing here goes beyond spec `0.23`. The tool reads only through zpf's
public reader. The truth lives in the tool and its report, never in the
`.zpf`. The two format questions in Phase 6 go to zipline as issues. They
are not worked around here.

## Sequencing and risk

- **No phase but a Phase 6 fix should move output.** `tools/byte_identity.py`
  against `v0.7.0` confirms it after each phase.
- **The risk is a scorer that is too easily satisfied.** On the capture
  path the expected answer is "perfect". A scorer that cannot tell
  conserved from withheld would agree with it. Hence a mutation in every
  scoring phase's *Done when*.
- **Phase 1 needs the network**, since the wheel installs from GitHub. So
  does every fresh venv, as `requirements.txt` already does today.
- **Phase 7 may not happen.** Its gate decides. The release does not wait on
  it.
