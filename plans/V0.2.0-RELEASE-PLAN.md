# Plan: the `v0.2.0` release

**Written 2026-09-12.** `0.1.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. Two issues sat on the `0.2.0`
milestone when this plan was started:
[#16](https://github.com/adamkjonsson/python-zipline-wire/issues/16) and
[#17](https://github.com/adamkjonsson/python-zipline-wire/issues/17).
**Only #16 is in this release.** Planning #17 showed that the part of it
that changes what a file says cannot be validated against anything real —
and it turned up a bug no issue names. Decision 1 records the hold; the
argument is in *What #17 turned out to need*.

| Issue | What it really is | In `0.2.0`? |
| --- | --- | --- |
| #16 | The **step onto packeteer 0.14.0**: one misfiled skip reason, one new fact to expose, one floor to raise | **Yes.** A day, and the tree already runs on the release it targets |
| #17 | The **first use of the TCP Timestamps option** in reassembly | **No — held for `0.3.0`**, on [packeteer#149](https://github.com/adamkjonsson/packeteer/issues/149) and [zipline#142](https://github.com/adamkjonsson/zipline/issues/142) |
| — | `overlap=favor-new` is accepted, hashed, documented — **and never read** | Decision 2 |

So `0.2.0` is a small release named for a sibling step, with one bug of our
own beside it. That is a legitimate release, and shipping it now rather than

### One thing no issue mentions

[`options.py:21`](../src/zpfwire/options.py#L21) offers two overlap policies,
`favor-old` and `favor-new`; [`options.py:88`](../src/zpfwire/options.py#L88)
validates them; `params_digest()` hashes them;
[`docs/guide/reassembly.md:82-96`](../docs/guide/reassembly.md) and the CLI
document them; [`test_cli.py:114`](../tests/test_cli.py#L114) passes
`--overlap favor-new` and checks the *digest*. **Nothing in `tcp.py` reads
`options.overlap`.** The reassembler trims every later copy against
`next_seq` and keeps the first held copy in `pending` — `favor-old`,
unconditionally. A file converted with `favor-new` carries a digest that
names a policy no code applied.

It was never implemented for a structural reason, which is the same reason
#17's `favor-acked` is not the small change the issue describes — see below.
Decision 2 is what `0.2.0` does about it.

## What #16 has to carry

From the issue, verified against our own tree rather than taken on trust.

### The misfiling, reproduced

```python
>>> buf = capture_of([b"\xff" * 40], link_type=LINKTYPE_RAW)
>>> reader = CaptureReader(file_object=buf); list(reader); reader.skipped
Counter({'unsupported-linktype': 1})
```

[`capture.py:341-343`](../src/zpfwire/capture.py#L341) infers the link layer
from three attributes being `None`. On `LINKTYPE_RAW` there is no link-layer
header to parse, so all three are `None` for *every* packet, and one whose IP
header fails is filed under a layer it does not have.

### One correction to the issue's step 2

The issue says that once the inference is deleted, "the `ethertype`/loopback
branches decide between `MALFORMED_IP` and `NON_IP` as they do today and the
raw-IP case falls into `MALFORMED_IP`". **It does not.** Checked against the
`0.14.0` parser: on `LINKTYPE_RAW` the link-layer walk returns
`ethertype=None` and sets no header object, and the failed packet arrives
with `offsets == {}` — nothing on the packet distinguishes it. Today's
ladder, minus its first branch, computes `ethertype = None`, finds it in no
IP EtherType, and answers **`NON_IP`**.

The fix is one fact the ladder does not have: **the link type**. A headerless
link type is itself the IP announcement — `LINKTYPE_RAW` *means* "raw IP" —
so a packet with no link-layer object on a supported link type is
`MALFORMED_IP`, by the same reasoning that makes an Ethernet frame with an IP
EtherType and no IP header `MALFORMED_IP`. `_unconvertible` has to be told
whether the capture is headerless, which `CaptureReader` knows and the packet
does not. That is the shape of Phase 1's change, and the regression test the
issue asks for is what would have caught the naïve version.

### The override lands in the header

`iter_packets(link_type=…)` writes the override into `header.link_type`
(verified), so [`CaptureReader.link_type`](../src/zpfwire/capture.py#L252)
already answers with the effective type and one
`supports_link_type(self.link_type)` in `__init__` covers both the file's own
value and `--link-type`.

### The warning

packeteer still parses every record of an unsupported capture, warning once
per call site via Python's own de-duplication. After Phase 1 we have already
said the same thing ourselves, up front and in our own words; the warning
becomes something packeteer says on our behalf, which #16 names as the thing
to stop. Scope a `warnings.catch_warnings()` filter for
`UnsupportedLinkTypeWarning` to the iteration in `__iter__`, and only when
`link_type_supported` is `False` — so a warning we did *not* anticipate still
surfaces.

### The four items, and what each rests on

| # | Rule | Changes bytes? | Rests on | Without real material |
| --- | --- | --- | --- | --- |
| (1) duplicate half | same TSval ⇒ duplicate | **Yes**: `retransmit` flag, Undecoded `reason` | a mirror copies bytes | sound by construction |
| (1) retransmission half | later TSval ⇒ resend | **Yes** | *a real resend never shares a clock tick with its original* | **unverified** — see below |
| (3) | late bytes: TSval older than the commit ⇒ delayed original; newer ⇒ recovered loss | No, stats-only | TSval monotonic per sender | near-tautological; small payoff alone |
| (2) | `favor-acked`: keep the copy the peer's TSecr echoes | Yes, for files that choose it | **holding every run until the peer acknowledges it** | structurally bigger than the issue says |
| (4) | PAWS | Yes, on wrap-adjacent streams | a wrap-adjacent capture | nothing to measure against |

**The retransmission half of (1) is the part that moves bytes, and it is the
part no synthetic capture can validate.** packeteer's clock ticks at 1 ms and
the issue calls a fast retransmit "safely apart"; Windows has historically
used a tick near 100 ms, and on a LAN a fast retransmit lands within one RTT,
well inside such a tick. A stack like that would have rule (1) call a real
retransmission a duplicate and *clear* the flag. That is exactly the class of
fact packeteer#127 says synthetic captures cannot surface, and shipping it
as a `Breaking:` entry validated only against frames written to satisfy the
rule is what that corpus was created to stop.

**And the flag's meaning is not settled.** The spec's token reads
*"retransmission/overlap was resolved inside this record"*; two other
passages use *retransmit* for anything the reassembler discarded. Rule (1)
takes the slash the first way — the sender's act — and a reader taking it the
second way would call our duplicated-capture files wrong. That is
[zipline#142](https://github.com/adamkjonsson/zipline/issues/142).

### Why (2) is not "one dict away"

The issue says the reverse direction's `_accept` already sees `pkt.ack`, so
"the TSecr lookup for (2) is one dict away". The *lookup* is. The *decision*
is not: the peer's echo arrives after the data it settles, and by then the
first copy has been appended to the run — or, on a `PSH`, already flushed
through `session.record()` and written. A single-pass writer cannot prefer a
copy against bytes it has emitted. Honouring `favor-acked` means a run stays
open past `PSH` until the peer's ack covers it, with a timeout for a
direction the capture does not hold, and the timestamp rule, `coalesce`,
`flush_timeout` and `--sequenced`'s own buffering all have to be re-argued
against that. It is the same structural fact that explains `favor-new`:
"prefer the retransmission" is unsatisfiable for bytes already written, and a
policy that holds only while a run happens to be open is not a policy.

## Decisions

### 1. Is #17 in `0.2.0`? — **No, held for `0.3.0`** (taken 2026-09-12)

The parts of #17 that survive without real material — the plumbing, the
late-bytes split, the duplicate half of rule (1) — have no user-visible
payoff on their own or a small one, and the part that has the payoff is the
part that moves bytes on a rule no real capture has confirmed. Splitting it
(ship the stats now, flip the flag later) was considered and declined: the
changelog would tell the "we started reading the option" story twice, and
in between the tool would contradict itself within one conversion — a
summary saying `duplicates 5 bytes` above a record flagged `retransmit`.

So the Timestamps work ships as one release with a real capture behind it
and the format's answer in hand. `0.3.0` starts from *What #17 turned out
to need* above; nothing there has to be rediscovered.

### 2. What happens to `favor-new`?

Three ways out of an option that does nothing:

- **Remove it (recommended).** `Breaking:` under `Changed`, migration line
  "use `favor-old`, which is what it always did". Digests already written
  with `favor-new` name a policy that was never applied; nothing can fix
  that, and continuing to write them makes more.
- **Implement it** — within the open run and `pending` only. That is a
  policy whose effect depends on where `PSH` fell, which is the reason it
  was never written; documenting the limit does not make it one.
- **Leave it, documented as a no-op.** Cheapest, and the one that keeps
  shipping a digest that lies.

Whichever is taken, the `favor-acked` issue from Phase 2 is where the
option's future is argued, and it should say that `favor-new` was withdrawn
for the same reason `favor-acked` needs a different reassembler.

### 3. Does `convert` refuse an unsupported link type?

Today it writes a valid, empty `.zpf` and prints `skipped N
(unsupported-linktype)` at the end. #16 asks that the fact be said up front;
it does not say whether to stop.

**Recommended: refuse, exit 1.** [`__main__.py:101-103`](../src/zpfwire/__main__.py#L101)
already refuses `--no-tcp --no-udp` because "nothing to convert" is not a
conversion, and this is the same case with the reason coming from the file.
`info` reports and continues, since reporting is its job. The API is
untouched either way: `CaptureReader` exposes the fact and `convert()` goes
on honouring the every-packet contract, so a caller who wants the empty
file can still have it.

## Sequencing and risk

**Phase 0 first, and it is not ours to do silently.** The one sibling
checkout this plan depends on is behind, and moving it is a change outside
this repository. Everything after it was verified against an exported tree,
which is the same code but not the same install.

**Phase 1 is the release.** It is small and certain, and its one
correctness risk — the `NON_IP` trap in the issue's own step 2 — is caught
by writing the regression test before the fix. The `cmp` check against
`0.1.0` output is what says Phase 1 touched nothing else.

**Phase 2's risk is only Decision 2.** Removing a CLI choice is a break in
the letter; the migration line makes it a no-op in practice, and the
`favor-acked` issue is what stops the argument from being lost.

**The thing this release does not risk** is the reassembler. No byte of any
fixture's output moves, and that is checkable, so the whole release can be
held to "same input, same options, same bytes as `0.1.0`" — the strongest
regression guard this project has, and one `0.3.0` will not be able to make.
