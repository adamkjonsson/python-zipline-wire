# Plan: the `v0.7.0` release

**Written 2026-10-26.** Draft. `0.6.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. The work is tracked by
[#52](https://github.com/adamkjonsson/python-zipline-wire/issues/52) on the
[`0.7.0` milestone](https://github.com/adamkjonsson/python-zipline-wire/milestone/7)
(Phase 0).

`0.7.0` is **the fidelity release**. It builds a tool that measures how well
a conversion's reassembled sessions represent the *true* traffic: the
conversation as both applications sent it, before the network damaged it.
packeteer generates a TCP conversation under impairments of our choosing and
knows exactly what was sent. zpfwire converts the impaired capture. The tool
scores the `.zpf` against what was sent.

`0.6.0` asked how *fast* the reassembler is, and answered with a benchmark
built in Phase 1 and quoted by every phase after it. This release asks how
*right* it is, and is shaped the same way: build the instrument, record a
baseline, and let what it finds decide the rest.

## Which project, and which version

**This is zpfwire `0.7.0`, not python-zipline `0.8.0`.** The tool needs
packeteer (to generate), zpfwire (to convert) and zpf (to read). zpfwire
already depends on zpf (`zpf>=0.7.0,<0.8`), so a tool inside python-zipline
would make python-zipline depend on zpfwire, which depends on it: a cycle.
It also measures zpfwire's reassembler, nothing of python-zipline's. Nothing
in this plan needs a python-zipline release. If the tool finds a defect
there, it is filed there (Phase 5), and its release follows python-zipline's
own milestones.

- **Siblings**: python-zipline `0.7.0` (spec `0.23`) and packeteer `0.20.0`,

- **A prototype exists.** It was run 2026-10-26 in `.venv`, against the

- **Filed from the prototype:**
  [packeteer#227](https://github.com/adamkjonsson/packeteer/issues/227), a
  corrupted segment that gets a valid checksum. Open, unmilestoned. It
  affects the truth this tool scores against (Decision 6).

### How the pieces fit

1. **Generate with packeteer's API, not its CLI**:
   `generate_tcp_stream(..., config=TCPStreamConfig(seed=…, messages=[AppMessage(…)], <impairments>))`.
   `tests/test_timestamps.py` already does this.
2. **Convert in memory**: `write_pcap(stream.to_pcap_tuples(), file_object=buf)`,
   then `zpfwire.capture_to_zpf(buf, out, options=…, produced_at=None)`.
3. **Read back**: `zpf.open(out).sessions()`, then `session.reassemble()`,
   then `view.chunks()`. That gives each direction as `Segment` and `Gap`
   runs, at logical offsets.
4. **Compare by offset.** A `StreamView`'s offset 0 is `isn + 1`, which is
   packeteer's sequence numbering too. Byte *k* of a direction's truth sits
   at offset *k*, with no alignment search.

### What the prototype found

Four messages (3,000 and 800 bytes client → server, 9,000 and 5,000 back), seed
3, position-unique payloads. Bytes wrong or missing, out of 3,800 c2s and
14,000 s2c:

| Impairment | Default | `favor-acked` | `checksum=drop` |
| --- | --- | --- | --- |
| none | 0 | 0 | 0 |
| loss 0.1, no recovery | 1,448 s2c missing, one gap | same | same |
| loss 0.1, `retransmit_lost` | 0 | 0 | 0 |
| corruption 0.2 | 1 c2s + 2 s2c wrong | **0** | **2 s2c wrong** |
| duplication 0.2 + retransmission 0.2 | 0 | 0 | 0 |
| 3 strays | 349 c2s wrong | 349 | 349 |
| server RST 0.3 | 0: **did not fire** at this seed | | |

Three things in that table shape the plan:

- **The `checksum=drop` row is packeteer#227, not zpfwire.** Two of the three
  corrupted segments carry valid checksums, so no checksum policy can catch
  them. The table is only evidence about zpfwire once the truth is known to
  be what it claims (Decision 6).
- **Strays win under every policy.** A forged segment that arrives first is
  kept by `favor-old`. `favor-acked` cannot help either: the receiver's
  acknowledgement covers a length, not content. But packeteer builds a stray
  **without a Timestamps option**, on a connection that negotiated it, and
  RFC 7323 §3.2 says a receiver SHOULD silently drop such a non-RST
  segment. That is a candidate rule for this reassembler, triaged in Phase 5.
- **A configured impairment is not a realised one.** The RST row scored
  perfectly because no RST was sent. Every result is reported against what
  the ledger shows happened (Decision 5).

## Phase 1: the truth and the ledger — **DONE** (2026-10-26)

What was sent, and what happened to it, built from the generator alone.
Nothing in this phase reads a `.zpf`.

**The truth.** A scenario is a list of `AppMessage`s, a seed, and an
`ImpairmentConfig`'s worth of fields. The truth for a direction is that
direction's messages, concatenated. That is independent of every impairment
by construction: packeteer sends each message whole, and a sender's sequence
number advances whether or not a segment arrives.

**Payloads are position-unique.** Each 16-byte block is a keyed hash of its
direction, message and block index. packeteer's default payload is repeating
text, where a run written at the wrong offset can match the truth there. With
unique blocks it cannot. A forged byte can still equal the truth by chance, 1
in 256. The report states that rather than hiding it.

**The ledger** is one entry per packet in `stream.packets`: direction,
`seq`, payload range, capture time, TSval, label kind (`DATA`, `RETRANS`,
`DUP`, `CORRUPT`, `STRAY`, `RST`, `ACK-RECOVER`, …), and whether its payload
equals the truth at its offset. Two things the list does not hold are
derived:

- **Lost segments.** They never enter `stream.packets`. A lost range is a
  truth range that no delivered packet carries.
- **True send times.** A segment's true time is its first transmission's
  capture time. A retransmission is the same bytes, later.

**Self-checks**, run on every generated stream, which void the run when they
fail:

- every `CORRUPT` packet fails its transport checksum (packeteer#227);
- every delivered `DATA` packet's payload equals the truth at its offset;
- the truth's length per direction equals the sum of that direction's
  messages.

### What Phase 1 execution changed

- **The code is `tools/fidelity.py`**, tested by `tests/test_fidelity.py`
  (33 tests, under a second). `pyproject.toml`'s pytest `pythonpath` gained
  `"tools"`, as Decision 2 said it would. The module imports packeteer and
  nothing of zpfwire's. Payloads and checksums come from packeteer's
  `parse_packet(raw, decode_app=False)`, not from `CaptureReader`, so the
  reference does not depend on the code it measures.
- **The scenario is the prototype's request/response order**: c2s 3,000, s2c
  9,000, c2s 800, s2c 5,000. Both orderings reproduce the corruption row.
  Only this one reproduces the stray row's 349 c2s bytes: two c2s strays of
  348 and 350 bytes.
- **Two generator facts the scenario has to pin.** packeteer sends
  `messages[i % len(messages)]` for each of `num_data_packets`, so that
  count is `len(messages)`. Without it a short list repeats. And
  `base_time` defaults to the wall clock, so it is fixed (`BASE_TIME`), or
  a seed reproduces everything but the timeline. A test holds a scenario
  to byte-identical generation.
- **The truth is not independent of a reset.** packeteer's RST pass removes
  every segment a side would have sent after it learned of the reset. Those
  bytes were written and never sent. So the truth stays what the
  applications wrote, and the ledger adds **`sent`**: how far each sender
  got, which is all of it unless an RST was captured. **`lost`** is then
  "sent and never captured", and a reset's unsent tail is not counted as
  loss. At seed 3 an RST leaves `sent` at c2s 3,000 and s2c 1,448, with
  nothing lost. A segment lost on the wire just before the reset is counted
  as unsent. That is the one imprecision, documented on `Ledger.sent`.
  Across 40 seeds of every impairment at once, each run that lost bytes
  despite `retransmit_lost` was a reset run whose resend fell after the RST.
- **Labels are split into kinds, outermost first.** packeteer drops `DATA`
  when it derives a label, so `RETRANS[2]` and `DUP[3] [1/4]` copy data
  segments, while `DUP[CORRUPT[1] [5/7]]` is `("DUP", "CORRUPT")`. An
  entry's true send time comes from its *original*: a `DATA` or `CORRUPT`
  copy. A segment whose original was lost has `sent_usec = None`, and Phase 3
  works from its resend.
- **The third self-check is stronger than "the lengths add up"**, which is
  true by construction. It checks that the generator's sequence space agrees
  with the truth: no non-stray segment ends past the truth, and every FIN
  sits at the truth's end. A truth one byte longer than what was sent fails
  both it and the payload check (tested).
- **packeteer#227 voids 20 of 40 runs** of the prototype at corruption 0.2,
  and **none** when data flows one way (`ONE_WAY`, 3,000 and 9,000 c2s). The
  rebuild only touches packets travelling opposite a corruption, so a
  corrupted segment is rebuilt only when both directions have one. Until
  Phase 6, corruption is scored on a one-way scenario. No other self-check
  fires on any seed of any impairment.
- **Shown to fail.** With the packeteer#227 check stubbed out, the seed-3
  corruption run is not void, and two of its three `CORRUPT` copies would
  be scored with valid checksums. The check was then restored.
- **Output unchanged**: `tools/byte_identity.py --baseline v0.6.0`, from
  `.venv`, 198 of 198 identical.

## Phase 2: the byte scorer — **DONE** (2026-10-26)

Per direction, every truth offset falls into exactly one class:

| Class | Meaning |
| --- | --- |
| **correct** | the output holds the true byte |
| **substituted** | the output holds a different byte |
| **missing, declared** | the offset is inside a `Gap` |
| **missing, past the end** | the offset is past the last `Segment`. `chunks()` never yields a trailing `Gap`, so a lost tail is visible only against the truth's length |

**Extra** is output past the truth's end. It is counted on its own.

Two ceilings separate what the network destroyed from what the reassembler
chose. **Available** is the truth offsets where some captured, non-stray
packet carries the true byte. Two scores follow:

- **fidelity**: correct ÷ truth length, what a reader of the file gets;
- **recovery**: correct ÷ available, what the reassembler made of what it
  was given.

A lost segment without recovery lowers fidelity and leaves recovery at 1.
A kept stray lowers both.

**Attribution.** Each substituted or missing range is mapped to the ledger
entries covering it: a `CORRUPT` copy kept, a `STRAY` kept, a loss never
recovered, a range available but dropped. This gives a confusion table per
impairment, and it is what turns a score into something to fix.

**Accounting** checks that the file and the stats tell the truth about
themselves:

- every captured payload byte that reached no record is cited by an
  `Undecoded` block, as `README.md` promises (*Nothing is lost quietly*);
- `stats.gaps` equals the ledger's count of unrecovered holes;
- a record's `RETRANSMIT` flag is set where the ledger shows `RETRANS` and
  clear where it shows `DUP`: precision and recall against the labels;
- the session's end reason matches the ledger: `rst` when an `RST` was
  delivered, `fin` otherwise.

Every conversion also passes this project's load-bearing assertion:
`reader.diagnostics == []` and `reader.unplaceable == []`. A file that fails
it is not scored. It is a bug in its own right.

### Done when

- [x] The prototype's clean, duplication-and-retransmission, and
  loss-with-recovery cases score fidelity 1 and recovery 1 over 40 seeds
  each, asserted in `tests/`. This is the one place a score is asserted
  (Decision 4).
- [x] **Shown to fail**, each mutation restored afterwards: the scorer's
  offset base moved by one; the `Undecoded` check fed a conversion with one

- [x] The confusion table is built for the prototype's corruption and stray

### What Phase 2 execution changed

- **`measure(run, options, sequenced=)`** converts in memory, reads back
  through zpf's public reader, and returns a `ByteScore` per direction and
  an `Accounting`. A file failing the load-bearing assertion raises
  `Unclean` and is not scored. A void run is still measured, because the
  tests need its numbers, but `Run.void` keeps it out of any report.
  `tests/test_fidelity.py` now has 48 tests, under 2 s.
- **The denominator is what was sent, not the truth's length.** That
  follows from Phase 1's `Ledger.sent`: after a reset, fidelity is measured
  against the bytes each sender sent, and *extra* is output at or past that
  point. Without a reset the two are the same.
- **Attribution is by byte, and needs no ledger lookup for most of them.**
  A missing byte is `missing:lost` where no non-stray packet carried it,
  else `missing:dropped`. A substituted byte is traced to a captured copy
  holding that exact value at that offset: `stray` or `corrupt`, or `other`
  if none does, which would be a bug. Nothing has scored `other` or
  `dropped` yet.
- **The prototype's rows reproduce**, asserted for all three policies:
  corruption is 1 c2s + 2 s2c / 0 / 2 s2c, strays 348 c2s under every
  policy. **348, not 349, and the scorer is right**: `STRAY[1]` (350 bytes,
  same offset, later) extends `STRAY[0]`'s 348 by its last 2 bytes before
  the real segment arrives, and 2 of the 350 forged bytes equal the truth
  by chance. The prototype's payloads were different, so its chance matches
  were too. This is the 1-in-256 case the plan said to state.
- **The `Undecoded` check works by multiplicity, not by sums.** Each
  citation is located in the capture: a payload's offset is computed from
  the stream, since `write_pcap` writes 24 + 16 bytes of headers, and that
  was verified against the written bytes. At every stream offset, the
  number of captured bytes no citation covers must equal the number of
  record bytes, and their values must agree. That catches a byte lost
  quietly, a byte both written and cited, and a byte written from the wrong
  copy. The stats' own identity cannot tell these apart.
- **The `RETRANSMIT` check is per packet, on the citation reason, not per
  record.** zpfwire sets the flag on whichever run is open when a repeat is
  discarded, not on the run holding the repeated bytes, so a record's flag
  cannot be scored against its own range. Each discarded repeat is cited
  with a reason, though, and that is the verdict the labels can check. A
  repeat is classed `copy` (`DUP`), `resend` (`RETRANS`), `original`
  (`DATA` or `CORRUPT`, losing to an earlier copy) or `stray`.
  **Measured over 40 seeds:** all 115 copies of an original are judged
  copies. **All 26 copies of a resend (`DUP[RETRANS[…]]`) are judged
  resends**, cited `overlap-discarded` rather than `duplicate-discarded`.
  zpfwire remembers only the transmission it kept, so a copy of a *discarded*
  resend looks like a new one. `test_a_duplicated_retransmission_is_both`
  says such a copy should be judged a copy. **A Phase 5 item.**
- **The end reason the ledger expects was wrong in the plan.** "`fin`
  otherwise" failed on 5 of 40 lossy seeds: packeteer never resends a lost
  FIN (`retransmit_lost` covers data only), so the capture holds one FIN,
  and zpfwire's `capture-end` is correct, since `fin` needs both. The
  expectation is now `rst` if an RST was captured, `fin` if both FINs were,
  else `capture-end`, still from the ledger alone.
- **Gaps against holes.** A hole is a range below a direction's furthest
  captured byte that no captured packet carries, strays included, since a
  stray can fill one. The check fails when `stats.gaps` differs from the
  file's `Gap` count, when the file has fewer gaps than holes, or when it
  has more and no bytes were late. None has failed.
- **Shown to fail.**
  - **The scorer's offset base moved by one** (`_compare(…, start + 1)`, on
    a copy): it fails loudly, with an `IndexError` at the stream's last byte.
    **The ledger's offset base moved by one** voids the run with 19
    self-check failures.
  - The sensitivity is also a permanent test: an output hand-shifted by one
    offset scores fidelity under 0.01.
  - **A conversion with one citation removed** reports exactly that
    citation's bytes as lost quietly (a test).
  - **A stream converted without its RST**, against a ledger that saw it,
    reports the wrong end reason (a test).
- **Output unchanged**: `tools/byte_identity.py --baseline v0.6.0`, 198 of
  198 identical.

## Phase 3: order and timing — **DONE** (2026-10-26)

**Order.** In a `messages` scenario the true causal order is the message
order. packeteer emits strictly in sequence, and each message after the
first carries an acknowledgement of the one before. The scorer finds each
message's first byte in `session.timeline()` and counts inversions. It does
so for an unsequenced conversion (the streaming merge) and for
`sequenced=True`. Every inversion is a failure. Neither path promises less
than a valid causal linearization.

**Timing.** For each message, the timestamp of the record holding its first
byte is compared with the true send time from the ledger. Errors are reported
as a distribution per impairment. A recovered loss is expected to be late by
about the retransmission timeout, and the report says so instead of calling
it an error. `ts_first` is reported beside `timestamp` where a record has
one.

**Not a clean twin.** True timing comes from the impaired run's own ledger,
never from re-running the seed with impairments off (Decision 3).

### Done when

- [x] Order and timing are scored for every Phase 2 scenario, default and
  sequenced.
- [x] **Shown to fail**: a hand-reordered `.zpf` reports its inversion.

### What Phase 3 execution changed

- **`measure()` now returns an `OrderScore`** with each message's position
  in `session.timeline()` and one `Timing` sample per placed message.
  `convert()` takes `face=` and keeps the file's bytes, so a test can edit
  a JSONL file by hand. `tests/test_fidelity.py` is at 70 tests, 2 of them
  strict xfails, in under 6 s.
- **The plan's premise about order fails under loss.** "Each message after
  the first carries an acknowledgement of the one before" is false once a
  segment is lost. packeteer keeps sending through the loss, and the
  receiver's ack stays at the hole, so a reply sent meanwhile acknowledges
  nothing of its request. At seed 1 with recovered loss, the reply really
  is placed first, and no wire evidence says it should not be. **What is
  scored is dependency, not message order**: *j* depends on *i* when *j*'s
  first segment, as first captured, acknowledged *i*'s first byte, or *i*
  is earlier in the same direction, closed transitively. A failure is *j*
  placed before an *i* it depends on. Plain message-order inversions are
  still reported, as `reordered`.
- **A forged first byte is set aside.** A stray that arrives before the
  real segment puts the message's first byte where the forgery arrived.
  `forged` counts those messages, and they take no part in the failure
  count. Without this, every stray run with an early forgery would show an
  "inversion" that no reassembler could avoid.
- **The finding: coalescing breaks causal order, on both paths.** zpfwire
  ends a coalesced run at PSH, at a close, or never. packeteer pushes a
  message's last segment with probability 0.5, its default. An unpushed
  request's run then carries on into the next request, *after* the
  server's response was received and acknowledged. The record holds bytes
  from both sides of the response, so no position for it is valid. The
  causal merge and `sequenced=True` both put it after the response, so the
  response precedes the request it answers. Over 40 seeds:

  | Scenario | PSH 0.5, coalesce | PSH 1.0, coalesce | PSH 0.5, `coalesce=False` |
  | --- | --- | --- | --- |
  | clean, duplication, dup + retransmission | 35 runs fail | 0 | 0 |
  | recovered loss | 18 | 0 (7 reordered) | 0 (8 reordered) |
  | loss | 17 | 0 | 0 |
  | stray | 16 (18 forged) | 0 (4 reordered) | 0 (1 reordered) |
  | RST | 7 | 0 | 0 |
  | corruption, one way | 0 | 0 | 0 |

  Identical under the merge and `sequenced=True` in every cell. A real
  stack pushes at the end of nearly every write, so real captures meet this
  less often than generated ones. The rule still never asks whether the
  peer spoke in between. `Scenario.psh_probability` was added (default
  0.5, packeteer's) to vary it. `test_an_unpushed_message_keeps_its_causal_order`
  is a **strict xfail** naming Phase 5, so a fix flips it. **A Phase 5
  item.**
- **Held segments lose their PSH on drain.** `TcpFlow` flushes on the
  arriving packet's PSH only. Segments drained from the reorder buffer
  coalesce across their own PSH boundaries: at seed 1, recovered loss
  joins requests 0 and 2 into one record. No dependency breaks there, since
  the reply did not acknowledge request 0, so it scores no failure. It
  feeds the same Phase 5 question.
- **Timing is per record, and coalescing sets its resolution.**
  - A record's `timestamp` is when its *last* packet arrived, so a message's
    error is how long the rest of its record took. The median is 4–6 ms,
    and the maximum is 22 ms unpushed or 12 ms pushed.
  - `ts_first` is exact (0) wherever the message starts its record. It is
    negative by up to 20 ms where an unpushed predecessor started the record.
  - A single-packet record has no `ts_first`.
  - zpf's per-unit `Segment.ts_for` cannot do better, because its
    contributors are file records, not packets.
  - **Recovered losses are late by the retransmission timeout:** 200–215 ms,
    on all 13 samples over 40 seeds. The true send time is the resend's less
    the timeout, which is how packeteer schedules it.
  - A record that coalesced a recovered hole is late by the same amount for
    every message in it: up to 219 ms for messages that were never lost.
  - Forged first bytes are timed as forgeries, 6 ms early at the median.
- **Shown to fail.** A sequenced JSONL file (pure ACKs off, PSH 1.0, seed 3)
  with the records of response 1 and request 2 swapped reads back clean,
  since the reader trusts a sequenced session's stored order and each
  participant's records are still in order. The scorer reports positions
  `(0, 2, 1, 3)` and one inversion. The unswapped file reports none.
- **`capture_to_zpf`'s `sink` annotation is wrong for JSONL.** It reads
  `str | PathLike[str] | IO[bytes]`, but `face="jsonl"` needs a text stream,
  which zpf enforces. The tool passes a `StringIO`, which runs and fails
  Pylance. A zpfwire fix, not a sibling's: **a Phase 5 item.**
- **Output unchanged**: `tools/byte_identity.py --baseline v0.6.0`, 198 of
  198 identical.

## Phase 4: the sweep, and a baseline — **DONE** (2026-10-26)

`tools/fidelity.py` runs a matrix: scenarios × impairment rates × seeds ×
reassembly policies (`favor-old`, `favor-acked`, `checksum=drop`, a tight
`reorder_window`/`flush_timeout`, `coalesce=False`, `pure_acks=False`). It
writes one JSON line per run, and a Markdown summary per (impairment,
policy) cell: median and worst fidelity and recovery, and the confusion
table.

- **What it ran against.** The header prints packeteer, zpf and zpfwire, each
  with `__version__` *and* `__file__`, as the pytest header does since #42.
  A baseline claimed for a release runs in `.venv`.
- **Realised, not configured.** A cell reports how many runs actually
  exercised its impairment. A cell exercised fewer than 10 times is marked
  *not exercised* and given no score.
- **Deterministic.** Seeded generation and `produced_at=None` make the same
  matrix produce the same report, byte for byte.
- **Scenarios** include at least: the prototype's four messages; one bulk
  transfer each way (≥ 1 MiB, so `reorder_window` binds); many small
  messages (so coalescing matters); and a delayed-ack shape for #32, whose
  covering ack arrives after `flush_timeout`.

The baseline, zpfwire `0.6.0` on packeteer `0.20.0` and zpf `0.7.0`, is
recorded in *What Phase 4 execution changed*. Every later phase quotes its
before and after against it, as `0.6.0` did with its benchmark.

### Done when

- [x] A default sweep runs in under five minutes and reports every cell.
- [x] The baseline is recorded in this plan.
- [x] `docs/internals/contributing.md` describes the tool beside
  `tools/byte_identity.py` and `benchmarks/reassembly.py`. `CHANGELOG.md`

### What Phase 4 execution changed

- **`.venv/bin/python tools/fidelity.py --out DIR`** runs the matrix and
  writes `runs.jsonl` (one line per conversion) and `summary.md` (one row
  per cell). `--shape` and `--seeds` narrow it, and `--jobs` sets the worker
  processes, one per CPU by default. It exits 1 if any conversion reads
  back unclean.
- **The matrix.** 7 scenario families × 15 impairment cells × 7 policies,
  for **23,520 conversions in 2 min 25 s** on 8 cores. Under five minutes,
  every cell reported.
  - **Families:**
    - the prototype, at packeteer's PSH rate and with PSH on every message;
    - 1 MiB each way;
    - 100 exchanges of 64 and 256 bytes, both PSH rates;
    - #32's delayed-ack shape.
  - **Impairments:** none; loss at 0.02 and 0.1, with and without
    recovery; retransmission, duplication and corruption at two rates each;
    duplication with retransmission (the prototype's row); 1 and 3 strays;
    RST.
  - **Policies:** `favor-old`, `favor-acked`, `checksum=drop`, `tight`
    (2,048 bytes, 10 ms), `no-coalesce`, `no-pure-acks`, `sequenced`.
- **PSH rate became a scenario dimension**, as Phase 3 showed it must. Each
  family carries its own seeds and RTO; the RTO is part of the path, so it
  overrides the impairment's.
- **The plan's reason for 1 MiB was wrong.** At packeteer's 1 ms gap, a
  0.2 s RTO holds about 145 KB behind a hole, inside the 256 KiB window, so
  the window does not bind however long the transfer is. The bulk families
  use **RFC 6298's initial RTO of 1 s**, which holds about 720 KB. Recovered
  loss then shows the window binding: recovery is 0.92 at the median and
  0.91 at worst, every lost byte `missing:dropped`, under every policy.
- **#32's shape needs no packet surgery.** packeteer's clean resend, and the
  covering ack behind it, arrive one RTO after the corrupted copy. An RTO of
  **6 s**, past the 5 s `flush_timeout`, is #32's condition exactly. It is
  one-way, so packeteer#227 cannot void it.
- **Deterministic**: two full sweeps, with 8 and with 3 workers, gave
  identical `summary.md` and `runs.jsonl`. Results are gathered in matrix
  order, and the report holds no timing.
- **A scorer false positive, found and fixed.** A message's dependencies
  were taken from its first *captured* copy. When the original is lost, that
  copy is a resend, carrying the ack of when it was resent. At `small-pushed`
  seed 2, one lost client message's resend made it, and through
  same-direction closure every later client message, appear to depend on a
  reply sent after it. Dependencies now come from the original transmission
  only, and a message whose original was lost has no ack evidence
  (`test_a_resend_s_ack_is_not_its_message_s`). The `tight` cells' spurious
  inversions went with it.

## Decisions

### 1. zpfwire `0.7.0`, not python-zipline `0.8.0`: **taken 2026-10-26**

As *Which project, and which version* argues: the dependency would be
circular, and the thing measured is zpfwire's. `0.7.0` rather than a patch
release, because Phase 5 may move bytes and Phase 6 moves a sibling's floor.

### 2. A tool in `tools/`, not public API: **recommended**

`tools/fidelity.py`, beside `tools/byte_identity.py`. It is not in the wheel
and carries no semver promise. The metrics will change as the baseline
teaches us what is worth measuring. Committing them as `zpfwire.fidelity`
in their first release would make every refinement a break. For the scorer
to be tested, `pyproject.toml`'s pytest `pythonpath` gains `"tools"`.

The alternative: a public `zpfwire.fidelity` with a `zpfwire fidelity` CLI
subcommand, so a user could choose `--reorder-window` or `--overlap` for
their traffic from evidence. It is worth doing once the metrics have
survived a release. It is a carry-over, not this release.

### 3. The truth is what was sent, never a re-run: **recommended**

packeteer draws everything from one `Random(seed)`. Loss is drawn inside
`emit()`, and a lost segment emits no ACK, which shifts every later
timestamp and jitter draw. Re-running the seed with impairments off gives
the same payload bytes (they are drawn before the emit loop) but a different
timeline. So bytes come from the messages, and times from the impaired
run's own ledger. A clean twin is never generated.

The truth is the *sender's* bytes, not the receiver's. A receiver that never
got a range still had it sent to it. That is "what the traffic would look
like without the impediments", and the *available* ceiling (Phase 2) is
what separates "the network destroyed it" from "the reassembler lost it".

### 4. Scores are reported, not asserted, except where they must be perfect: **recommended**

As `0.6.0` Decision 4 did for timings. A threshold on a lossy cell would be
arbitrary, and would turn every improvement into a test edit. The cases
where perfection is *required* are asserted: no impairment, duplication,
spurious retransmission, recovered loss. A regression there is a bug,
whatever the matrix says.

### 5. Results are conditioned on what happened: **recommended**

A cell is scored from the ledger's realised impairments, never from the
configured probabilities. The prototype's RST row is the reason: it looked
like a perfect result and was an untested one.

### 6. No shim for packeteer#227: detect and void: **recommended**

Upstream-first. The tree does not re-corrupt packets that packeteer
rebuilt. The Phase 1 self-check finds such a packet and voids the run, which
keeps the tool honest about its own input. The void count is itself a
result, and it tells packeteer how often #227 bites.

### 7. TCP only: **recommended**

UDP needs different measures: which datagrams arrived, how many times, in
what order. Datagram reordering, the one impairment packeteer offers only
there, is unmeasured until then. SCTP refuses every impairment. A UDP
extension is filed as a carry-over in Phase 7.

## Format notes

Nothing here goes beyond spec `0.23`. The tool reads only through zpf's
public reader: `sessions()`, `reassemble()`, `chunks()`, `timeline()`,
`undecoded()`, `end`. The truth lives in the tool and its report, **never
in the `.zpf`**. Storing it there, as an extra Source or a stage, would
claim a provenance the file does not have.

## Sequencing and risk

- **Phases 1–4 change no output.** `tools/byte_identity.py` against `v0.6.0`
  confirms it after each one.
- **The size of the release is unknown until Phase 4.** Phase 5 decides it
  from the baseline. The plan commits to the instrument and to triaging what
  it finds, not to a list of fixes.
- **The main risk is a wrong scorer**, which would send fixes after
  phantoms. Hence the mutations in every *Done when*, and the self-checks
  that void a run rather than score a doubtful one.
