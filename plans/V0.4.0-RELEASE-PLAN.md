# Plan: the `v0.4.0` release

**Written 2026-09-19.** `0.3.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. The `0.4.0` milestone is
described as *"Alignment with zipline 0.21 and python-zipline 0.5.0"*, and
that is the whole of it: both siblings released on 2026-09-18, one day after
`0.3.0`, and the [`0.3.0` plan](V0.3.0-RELEASE-PLAN.md#what-040-starts-from)
ends by naming the two upstream issues this release was always going to be
about. Five issues sit on the milestone. One is the upstream notice; the four
under it were split out of it for this plan
([#25](https://github.com/adamkjonsson/python-zipline-wire/issues/25#issuecomment-5742599209)),
and **all four are in**.

| Issue | What it really is | In `0.4.0`? |
| --- | --- | --- |
| [#25](https://github.com/adamkjonsson/python-zipline-wire/issues/25) | The upstream notice for python-zipline `0.5.0` — the umbrella | Closes with the four below, at release |
| [#26](https://github.com/adamkjonsson/python-zipline-wire/issues/26) | **The stamp**: `zpf>=0.5.0`, the `v0.21` Specification URL, the `0.20` mentions, the changelog entry | **Yes** — Phase 0; the one failing test today |
| [#27](https://github.com/adamkjonsson/python-zipline-wire/issues/27) | **The [zipline#146](https://github.com/adamkjonsson/zipline/issues/146) shim goes**: a direction longer than 2 GiB is one session. Two public names removed | **Yes** — Phase 1; the reason this is a minor |
| [#28](https://github.com/adamkjonsson/python-zipline-wire/issues/28) | **`capture-gap` is the specification's word** ([zipline#147](https://github.com/adamkjonsson/zipline/issues/147)): cite it, and pin the half of its exit the suite does not check | **Yes** — Phase 2 |
| [#29](https://github.com/adamkjonsson/python-zipline-wire/issues/29) | **`adjacency`**, the first body field since `0.15`: document that every participant here is `contiguous`, and pin it | **Yes** — Phase 3 |
| — | The three things the `0.3.0` plan left for `0.4.0` that are *not* alignment | **No** — Decision 2 |

So `0.4.0` is **the spec `0.21` release**, and unlike the `0.20` port folded
into `0.3.0` it is not just a stamp: `0.21` changes what a reader *computes*,
and the thing it changes is precisely the ceiling this project hit in
`0.3.0` and shimmed around. The shim was written with its own deletion list;
this plan is mostly that list, plus the two rulings that landed beside it.

**One failure, and it is the guard doing its job** — the URL is the one
piece of version metadata that cannot be derived at runtime, so it is the
one that drifts, and [`test_package.py:45`](../tests/test_package.py#L45)
exists to make it fail loudly. Everything else is green on `0.5.0` without a
line changed, which says three things worth stating rather than assuming:

- **No API this tree calls moved.** `SessionWriter.participant()` gained a
  keyword with a default; `record()`, `undecoded()`, `Hints`, `Decoded`,
  `RecordFlags`, the Undecoded reasons and `reason_class` are as they were.
- **No participant byte moved.** The sixteen decode pins in
  [`test_pins.py`](../tests/test_pins.py) hash every Participant block's
  `to_bytes()`, which now includes the `adjacency` byte at offset 10. They
  hold, so the byte the `0.4.0`-era writer put there as `_reserved = 0` and
  the byte the `0.5.0` writer puts there as `contiguous = 0` are the same
  byte. The only thing that moves in any file this tree writes for the same
  input and options is the version stamp in the File Header — until Phase 1.
- **Every fixture still reads clean**: `diagnostics == []` and
  `unplaceable == []` on all twenty-two, under both overlap policies where a
  test asks.

And the one measurement that is not in the suite, because the suite pins the
shim: with `tcp._OFFSET_LIMIT` set past reach and nothing else changed,
`test_tcp.py`'s `_long_stream(5)` — the handshake, then one 4-byte segment
per GiB — converts as **one session**, `end_reason == "capture-end"`, and
reads back

```
10.0.0.1:51000  isn=1000  adjacency=0
  ranges=[(0, 0), (0, 4), (1073741824, 1073741828), (2147483648, 2147483652),
          (3221225472, 3221225476), (4294967296, 4294967300)]
diagnostics: []  unplaceable: []
```

Five records placed at 0 through 4 GiB, the last of them past 2³² from the
origin, where `0.3.0`'s shim would have written three sessions. The trigger
the shim's comment names has fired; Phase 1 is the deletion.

### What `0.21` says, and what reaches a capture-sourced transport-layer producer

The `0.20` port could say "no rule this library did not already keep was
introduced". `0.21` cannot; it is *the design release*, two rulings and no
option, and this tree is the reason one of them exists. From
[zipline's changelog](../../zipline/CHANGELOG.md) and
[python-zipline's](../../python-zipline/CHANGELOG.md), read against the
code rather than taken on trust:

| `0.21` item | What it is | Reaches us? |
| --- | --- | --- |
| **Offsets unwrap along stored order** ([zipline#146](https://github.com/adamkjonsson/zipline/issues/146), filed from #17) | Record *k*'s offset is record *k−1*'s plus the signed serial delta of their `seq_start`s; the first's is its delta from the origin. Well-defined at any length because the ordering rule keeps consecutive records within 2³¹. Two vectors: `stream-past-2gib`, `stream-wraps-seq` | **Yes, directly.** It is what the shim waited for. python-zipline `0.5.0` walks every path this way — `record_ranges`, `stream_extent`, the views, the checker, the writer's placement guard — and closes [python-zipline#70](https://github.com/adamkjonsson/python-zipline/issues/70) with it |
| **The floor binds each record to its predecessor**; an unplaceable record anchors nothing | *Clarified*, not changed: "below the origin" and "out of order" were one case seen twice | **Not as code.** This tree never writes an unplaceable record — the checked writer refuses one — and `reader.unplaceable` still means what the tests assert. Its note now names origin or predecessor |
| **`capture-gap` is a Session End reason** ([zipline#147](https://github.com/adamkjonsson/zipline/issues/147), filed from #17) | The one hole the walk cannot place — ≥ 2³¹ between consecutive records — gets no representation; the producer ends the session and opens another on the same key with no `isn`, and **SHOULD** write `capture-gap`. Vector: `session-split-capture-gap` | **Yes, and it is already what we do.** `END_CAPTURE_GAP = "capture-gap"` and the first branch of `splits_before` are the spec's exit, chosen here in `0.3.0` before the spec named it. Nothing moves; the docstrings and docs get a section to cite |
| **`adjacency`, a Participant body field** ([zipline#80](https://github.com/adamkjonsson/zipline/issues/80), [#106](https://github.com/adamkjonsson/zipline/issues/106)) | The reserved `u16` after `participant_id` is `adjacency: u8` + `_reserved: u8`. `0` = `contiguous`, `1` = `units` (a unit sequence). Third load-bearing enum. A writer **MUST NOT** set `units` on a transport-layer participant | **Yes, inertly.** Every participant here is transport-layer, so `contiguous` is the only conformant value and the `0.5.0` default writes it. A body field always projects, so every participant `.jsonl` line grew `"adjacency"` — nothing here compares JSONL |
| **Package D declined**; the `u64 offset` option deferred to `1.x` | *Decided.* `input_extents`, `reason_class`, the seam predicate stay | **No.** This tree writes no Discontinuity and no `zpf-input` Source, and `reason_class` on `Undecoded` was never under threat here. The deferral is why a converted stream still *ends* at a wide hole rather than spanning it |

Three of five reach the tree; one as a deletion, one as a citation, one as a
test. That is the shape of the phases.

### What Phase 1 execution changed

- **Deleting the shim exposed a second defect the shim had been hiding**,
  and it is the release's real finding. The inverted
  `sequences_cleanly` test failed against `zpf` 0.5.0: the causal guard
  (`_check_not_already_acked`, `seq_geq(max_ack, end)`) compares a
  record's end against the peer's latest *recorded* `ack` by serial
  arithmetic, and the synthetic peer's only record is its SYN-ACK
  (`ack = 1001`), so the client record ending 2³¹ past it reads as already
  acknowledged. Measured on three peer shapes: silent and pure-ACK both
  refuse at the 2 GiB record under `sequenced=True`; a peer that sends
  data with current acks passes; all three are clean without `sequenced`.
  The pure-ACK peer is an ordinary upload — a pure ACK carries no payload
  and leaves no record — and `0.3.0`'s split reset `max_ack` every 2 GiB
  before the comparison could invert. It is spec §Causal ordering step 2's
  premise ("within any in-flight window") that is false, in exactly the
  way #146 showed the origin floor's was: the compared values are a record
  end and an *older record's* ack, a whole stream apart.
- **Filed, after asking**: [zipline#151](https://github.com/adamkjonsson/zipline/issues/151)
  (the rule; acks unwrapping along the acker's stored order as the
  candidate fix) and [python-zipline#75](https://github.com/adamkjonsson/python-zipline/issues/75)
  (the refusal, with a standalone `zpf` repro run before posting — it
  needed `sequenced=True` as well as `linearize=True` to trigger, which
  the first draft of the snippet did not have).
- **Decided, after asking: delete the shim and record the limit; no new
  shim.** Plain conversion of the shape is the headline and works. The
  pure-ACK-peer sequenced shape is `test_a_sequenced_upload_past_2_gib_with_a_pure_ack_peer`,
  `xfail(strict=True, raises=SemanticError)` naming #151; the data-peer
  shape is what `test_a_long_stream_sequences_cleanly` now asserts, with
  `verify_sequenced` on the read-back as before. `limits.md` has a
  paragraph, the changelog a third **Breaking** entry — a `0.3.0`
  sequenced conversion of such a capture succeeded and a `0.4.0` one
  raises — and `upstream-first.md` explains why this one is not shimmed.
- **The tests**: `GIB`, `_long_stream` and the section stay under a new
  heading; two tests inverted as planned, the straddling test became
  *far-from-origin-near-predecessor* with an extent assertion, and a
  `_client_extent` helper reads `zpf.stream_extent` from the file
  (`participant, stream_blocks(pid), layer(pid)` — the reader has no
  one-call extent). `tcp_wrap_ts` gained its extent assertion, `65536`
  under both policies: the offset space is hole-inclusive, so the bytes
  `no-hold` loses are still in it. No CLI test named the `offset` line.
- **`_SEQ_HALF` stays** — `_delta` uses it; only `_OFFSET_LIMIT` went.
- **Decode digests: 44 of 44 identical** across the phase — 22 fixtures ×
  two policies, `produced_at=None`, computed from the stash and the tree.

### Two habits

Both of the new items above are meant to outlive this plan, which is why
they are also written into [`CLAUDE.md`](../CLAUDE.md)'s release steps
rather than only here — a plan is historical, and a habit that lives only
in one is a habit for one release.

**The sweep** exists because each release so far has found a stale sentence
the previous one left: `limits.md` said "without a version constraint" from
`0.1.0` to `0.2.0`, and quoted `0.3.0`-era floors through `0.3.0`. Issues
fix the sites they name; nobody names the site nobody noticed. One pass,
at the end, reading rather than grepping, is cheap next to a reader trusting
a page that is wrong.

**Filing the carry-overs** exists because the plans' closing sections have
been doing the tracker's job. The `0.3.0` plan's *What `0.4.0` starts from*
listed five items; two became this release because upstream released, and
three would have been lost to a section of a historical document had this
plan not re-read it. An issue is visible from the milestone view, can be
commented on when its premise changes (as packeteer#163's did the day after
it was deferred), and closes when done. The rule, from here on: **anything
a plan defers — to a later release here or to a sibling — is an issue
before the release is tagged**, and the plan links the number. For a
sibling, the existing rule stands: ask before filing, then file.

## Decisions

### 1. Is it `0.4.0` or `0.3.1`? — **`0.4.0`** (taken 2026-09-19)

Two independent reasons, either sufficient. The spec port alone is a
minor: a `0.21` file is refused by a `0.20` reader, and `0.3.0`'s own
changelog says a `.zpf` whose bytes move for the same input is a break —
python-zipline made the same call for its `0.5.0`. And #27 removes two
public names and changes what a >2 GiB conversion writes, which is a
**Breaking** entry on its own terms. A patch would have to keep the shim,
and a shim whose trigger has fired is not temporary any more.

### 2. What the `0.3.0` plan left for `0.4.0`, and is not here (taken 2026-09-19)

[*What `0.4.0` starts from*](V0.3.0-RELEASE-PLAN.md#what-040-starts-from)
listed five items. Two are #146 and #147 — this release. The other three
are **not** in it:

- **The generated `favor-acked` test** (packeteer#163, fixed in `0.16.0`):
  a seeded corrupt-then-resend stream asserting one swap per corruption
  and `favor-acked == checksum="drop"`. It wants the packeteer floor at
  `0.16.0`, and this release does not otherwise touch packeteer. Moving a
  floor for a test's sake was declined once already, in `0.3.0`'s Phase 5;
  the milestone says *alignment*, and the floor is not part of that.
- **The fifth site**: a held segment wholly superseded by the fill never
  sets `retransmit`. A reassembly-policy question the pins deferred; it
  moves bytes on real fixtures and deserves its own issue and measurement,
  not a bullet in a port.
- **A dedicated bound for the `favor-acked` hold** (0.3.0 Decision 3): only
  from a capture that needs one, and none has.

They roll forward under *What `0.5.0` starts from*, and the first is worth
an issue when the next packeteer step comes.

### 3. Phase order: stamp first (taken 2026-09-19)

Phase 0 before Phase 1 rather than the shim first, because the suite is
red today on the URL guard and every phase's *done when* wants it green.
The `0.3.0` plan did the stamp last, under the release phase, because the
sibling had not released when the plan was written; here both had, and the
stamp is a day's work that makes every later measurement clean.

### 4. Two tests inverted, two kept, none merely deleted (taken 2026-09-19)

The shim's four tests were written to be deleted "with the shim". Deleting
them would leave the suite with no stream past 2 GiB — the one shape
`0.21` exists for and the one this project reported. So each becomes the
assertion of the rule it was working around, and the section stays under
a new heading. The `stream_extent` assertion on `tcp_wrap_ts.pcap` is the
same idea applied to the real capture.

## Sequencing and risk

Four phases, in order, each leaving the suite green; a day, perhaps two.
The risk is small and specific:

- **Something else reads `_Stream.origin`.** The word appears 29 times in
  `tcp.py`, nearly all in prose about the offset origin that stays correct;
  the field, its two assignments and the one read in `splits_before` are
  all the code uses. `grep` after the deletion and read the survivors.
- **The straddling test's inversion is subtler than it looks.** Under the
  new rule the interesting case is *far from the origin, close to the
  predecessor*. The existing pair (`ISN + 1`, `ISN + 1 + 2³¹ − 2`) is 2³¹ − 2
  apart — under 2³¹, so it must place. Add the pair at exactly 2³¹ apart
  only if it is worth pinning that the ordering rule *refuses* it, and
  that refusal is the checked writer's, not ours: our reassembler would
  have to be handed such a pair without the Timestamps option to reach the
  writer at all, and without the option it discards the second as a repeat
  before the writer sees it. That is the existing
  `test_without_a_newer_clock_the_far_side_of_a_hole_is_old_data` shape,
  not a new test.
- **Docs build.** `docs/api/flow.md`'s `autodata` for a deleted name fails
  the Sphinx build, not the suite. Build once in Phase 1.
- **The decode-digest check across Phase 1** is the release's whole
  regression guard for the sixteen pinned fixtures *and* the six
  unpinned ones; run it, do not reason about it.
