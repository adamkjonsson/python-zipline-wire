# Plan: the `v0.9.0` release

**Written 2026-10-30.** `0.8.0` is tagged and `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md) is empty. python-zipline released `0.8.0`
the same day, implementing spec **`0.24`**, and left three issues here. The
work is five issues on the
[`0.9.0` milestone](https://github.com/adamkjonsson/python-zipline-wire/milestone/9):

| Issue | What | Kind |
| --- | --- | --- |
| [#73](https://github.com/adamkjonsson/python-zipline-wire/issues/73) | Port to python-zipline `0.8.0` (spec `0.24`): re-vendor, the new distribution name, a trailing `Gap` the fidelity scorer does not expect | port |
| [#76](https://github.com/adamkjonsson/python-zipline-wire/issues/76) | `stats.gaps` misses the hole under a pure ACK written at the end of a session, so a lossy conversion reports clean | bug |
| [#74](https://github.com/adamkjonsson/python-zipline-wire/issues/74) | A datagram whose fragments never all arrived leaves no trace on the capture path; `0.24` makes the citation a `MUST` | bug, conformance |
| [#75](https://github.com/adamkjonsson/python-zipline-wire/issues/75) | `packets_to_zpf` can write a reassembled UDP datagram as one `message` record | enhancement |
| [#77](https://github.com/adamkjonsson/python-zipline-wire/issues/77) | Mark a UDP datagram the capture saw twice with `copy`, when zpfwire can tell | enhancement |

`0.9.0` is **the spec `0.24` release**. #73 makes the tree run on the new
library. #74 is the one new requirement this tree does not meet. #75 and
#77 take up two things `0.24` now permits, and both answer questions this
project filed: zipline#166 and zipline#169. #76 is a bug of ours that the new
reader made visible.

## Which project, and which version

**zpfwire `0.9.0`**, against spec `0.24`, python-zipline `0.8.0` and
packeteer `0.21.0`. A minor bump with several **Breaking** changes:

- **The format.** Every file is stamped `0.24`. Under the `0.x` rule, `0.23`
  readers refuse it, and this release cannot read `0.23` files.
- **The dependency string.** zpf is now distributed as `python-zipline`
  (python-zipline#102), so the declaration from #67 becomes
  `python-zipline @ git+…@v0.8.0`. An existing venv must
  `pip uninstall zpf` first, or the old distribution's metadata stays
  behind.
- **Bytes a conversion writes**:
  - a capture with an incomplete fragmented datagram gains `Undecoded` blocks
    (#74);
  - a `.zpf` of packets holding a fragmented UDP datagram gains its record
    (#75);
  - a capture holding a markable copy gains a `copy` flag (#77).
- **`SKIP_FRAGMENTED_UDP` is removed** (#75, decided 2026-10-30).
- **`zpfwire.fidelity.ByteScore.missing_past_end`** counts less: a lost tail
  that a later record reaches is now a declared hole (Decision 4).

## Where the tree stands

- **`main` is `0.8.0`** (`90467bf`, the plan's completion on top of the
  release merge `1a7f7e0`). Nothing has landed since.
- **The siblings** are python-zipline `0.7.0` (spec `0.23`) and packeteer
  `0.21.0`, each declared by its release tag (#67).
- **Against python-zipline `0.8.0`**, measured 2026-10-30 in a throwaway
  venv with this tree, `v0.8.0` of python-zipline and `v0.21.0` of
  packeteer:
  - **The suite**: 14 of 1,683 tests fail, exactly the four causes #73
    lists. Six come from the vendored `0.23` tunnel vector, two from
    `test_package`, five from the scorer's trailing `Gap`, and one from a
    lost FIN.
  - **The fidelity sweep** stops at its first lossy TCP run, on the scorer's
    `a hole that is not a Gap`.
  - **With the scorer's `past_end` measured from the end of the last chunk**,
    gaps included (in a scratch tree), all 42,576 conversions run. **537
    fail accounting**, every one of them `stats.gaps` short of the file by
    one, or by two with both directions affected. That is #76. They are all
    TCP loss cells, spread evenly over every policy. The sweep's own hole
    count is short by the same amount, since it stops at the last captured
    *data* byte where `0.24`'s extent runs to the last sequence number.
  - **Nothing else moves.** Fidelity, recovery, causes, order, timing,
    judgements and every UDP number are identical to the `0.8.0` baseline
    (`8ffd6944…`, regenerated the same day). The one other change is 281
    directions whose missing bytes move from *past the end* to *declared*.
- **No packeteer change is needed for #74.** Each `IncompleteDatagram`
  carries `tokens`, the `PcapRecord`s of the fragments that did arrive,
  whose `data_offset` is the byte to cite.
- **packeteer's generator cannot make a markable copy** for #77. It builds
  every datagram with IP identification 0, and gives a duplicated fragmented
  datagram a fresh ID (packeteer#232).

## Phase 2: `stats.gaps` under a final pure ACK (#76)

`TcpFlow.finish()` writes the pure ACKs still ahead of the frontier "last,
in order" (`tcp.py:589–594`), without committing the hole below them. It
should record that hole as a committed gap, in `stats.gaps` and
`committed_gaps`, as `_commit_remaining` does for held data. A lost FIN's
position is that hole when no record carries `fin`.

## Phase 3: cite every incomplete datagram on the capture path (#74)

`CaptureReader` counts a datagram that never completed under
`SkipReason.INCOMPLETE_DATAGRAM`, and nothing goes in the file. `0.24`
requires an Undecoded block against the `capture` source for its pieces,
`reason = undecodable`.

- **One block per fragment that arrived**, covering its frame's captured
  bytes. The location comes from packeteer's `IncompleteDatagram.tokens`:
  each is a `PcapRecord`, and its `data_offset` is the byte to cite. That
  is what the `capture-fragment-lost` vector cites: bytes `[40, 106)`, the
  whole frame.
- **A `comment`** says what was missing: the fragments seen, the bytes
  expected, and why it was abandoned, from the `IncompleteDatagram`'s own
  fields.
- **TCP too** (decided). For TCP, the sequence numbers already show the
  hole, but the pieces that did arrive would leave no trace.
- **Where the blocks go.** The reassembler reports incomplete datagrams only
  after iteration, so the blocks are written when the capture is exhausted.
  This phase checks that a file-level Undecoded against the `capture` source
  may follow the sessions. If the writer refuses, that is a question for
  python-zipline, asked first.
- **`skipped[INCOMPLETE_DATAGRAM]`** stays as the tally.
- **A fixture.** No capture here has an incomplete datagram:
  `fragmentation.pcap`'s all complete. A test builds one, a UDP and a TCP
  datagram each missing a fragment, with `tests/helpers.py`'s
  `fragmented_frames`. The `capture-fragment-lost` vector is vendored and
  converted, and its Undecoded block compared.
- **The related limit.** `docs/reference/limits.md` says a discard from a
  datagram reassembled from several fragments is counted as
  `unlocatable_bytes` and not cited, because one block names one range.
  This phase builds per-fragment citation, which is the same machinery.
  Whether to retire that limit too is decided here. It is in scope only if
  it is small, and otherwise it is a carry-over.

### Done when

- [ ] The vector's block reproduces, and the tests show each fragment that
  arrived cited, for UDP and for TCP. **Shown to fail**: with the blocks
  removed, the tests fail.
- [ ] `tools/byte_identity.py` against `v0.8.0` names no fixture moved, since
  none has an incomplete datagram. If one does, it is named.
- [ ] `CHANGELOG.md`, under *Changed*: **Breaking**, since bytes move for a
  capture with an incomplete datagram. `docs/reference/zpf-mapping.md`

## Phase 4: a reassembled UDP datagram on the packets path (#75)

`0.24` lets a transport record flagged `message` cite several input units,
or cross a declared break (zipline#166). python-zipline `0.8.0`'s
`FlowSession.record` accepts several `cites` with `RecordFlags.MESSAGE`.

- **A reassembled UDP datagram is one record**, flagged `message`, citing
  every fragment it was built from. **Its time is its last fragment's**,
  with `ts_first` for the first. That is the spec's rule, the capture
  path's, and what the `0.8.0` fidelity tool pinned. The
  `sessionized-fragments` vector stamps the first fragment's time instead,
  an open vector defect (zipline#175), and is not followed there.
- **A datagram that never completed** is marked through
  `SessionizeStage.incomplete()`, `undecodable`, and counted under
  `SkipReason.INCOMPLETE_DATAGRAM` as now.
- **`SKIP_FRAGMENTED_UDP` is removed** from `zpfwire`, `__all__`, the API
  guide's table and `docs/guide/converting-packets.md`.
- **The fidelity tool** (`tools/fidelity_udp.py`): the packets path now
  writes fragmented datagrams.
  - `udp-fragmented`'s packets cells should conserve 1, as the capture path
    does, and the provenance check must accept a record citing several
    frames.
  - The tests that pin the old withholding are rewritten to pin the new
    record: the prototype table's packets row, the no-session test and
    `test_the_packets_path_withholds_a_fragmented_datagram_and_cites_it`.
  - A *lost*-fragment UDP cell needs packeteer to lose a fragment rather
    than a datagram, which it cannot: its loss is applied before
    fragmentation. That is noted, not filed, unless this phase finds it
    worth asking for.
- **The vector** `sessionized-fragments` is converted, and its record
  compared with what this tree writes, the time aside (zipline#175).

### Done when

- [ ] On the packets path, a fragmented UDP datagram is one `message` record
  citing its fragments, and an incomplete one is cited `undecodable`.
  **Shown to fail** on the old tree.
- [ ] The UDP sweep's `udp-fragmented` packets cells conserve 1 with no
  accounting failure, and the packets path differs from the capture path
  nowhere.
- [ ] `tools/byte_identity.py` against `v0.8.0` names the fixtures whose

- [ ] `CHANGELOG.md`: under *Changed*, **Breaking**, since packets-path

## Phase 5: the `copy` flag (#77)

Optional under `0.24`: a producer that cannot tell leaves it unset. The rule
here is the conservative one from #77. The flag is set when:

- the record immediately follows its original among its participant's
  records, as the spec requires;
- the two IP datagrams are byte-identical, with the same **non-zero**
  identification. A resend gets a new ID, while a mirror repeats the
  packet. A datagram with ID 0 cannot be told from an application resend,
  and is left unset.

The work:

- **`PacketView`** carries the IP identification, or a digest of the IP
  datagram, from packeteer's parse.
- **`UdpFlow`** keeps each participant's previous datagram and sets
  `RecordFlags.COPY` when the rule holds. The writer's conformance checker
  refuses a wrong flag, which is a second guard.
- **Tests** build the shapes with `PacketBuilder.ip(identification=…)`,
  through `tests/helpers.py`'s `udp_packet`:
  - a mirror copy is marked;
  - an application resend with a new ID is not;
  - ID 0 is not;
  - a copy that does not immediately follow its original is not.
- **The fidelity tool cannot exercise it** until packeteer's generator
  stamps non-zero, seeded IDs and repeats them on a duplicate (packeteer#232
  is half of it). That request goes to packeteer, **asked first**. Until
  then, the sweep's *repeated* column is unchanged.
- **Docs**: the limits page's entry from `0.8.0` Phase 6 ("the format has no
  way to mark a record as a copy") is rewritten. The zpf mapping's `flags`
  row gains `COPY`.

### Done when

- [ ] The four shapes pass, and the marked one reads back clean.
  **Shown to fail**: a `copy` forced on a record whose payload differs is
  refused by the writer.
- [ ] `tools/byte_identity.py` against `v0.8.0` names any fixture that
  gains a flag. Likely none: `udp.pcap` and `dns_example.pcapng` hold no
  repeats.
- [ ] `CHANGELOG.md`: under *Added*, and **Breaking** under *Changed* for
  the bytes a marked copy moves.

## Decisions

### 1. The port first, with no behaviour moved: **recommended**

Phase 1 changes only what running on the new library forces, so that each
later phase's before and after is measured on the same library. The two
scorer fixes are in Phase 1 because the sweep cannot run without them.

### 2. #74 covers TCP: **taken 2026-10-30**

Recorded on the issue.

### 3. `SKIP_FRAGMENTED_UDP` is removed: **taken 2026-10-30**

Recorded on the issue.

### 4. `ByteScore.missing_past_end` changes, and is called Breaking: **recommended**

`zpfwire.fidelity` has been public for one release. The field's definition
does not change: bytes past the last thing the file shows. What changes is
the reader, which since `0.24` shows a hole that a later record reaches. A
caller comparing numbers across the upgrade sees 281 of the sweep's
directions move from one field to the other, with the total unchanged. A
promised number moves, so it is marked **Breaking**, with the reason.

### 5. A reassembled datagram takes its last fragment's time: **recommended**

As Phase 4 says. The spec's rule and the capture path's agree, and the vector
that disagrees is a filed defect (zipline#175).

### 6. `copy` only when zpfwire can tell: **recommended**

The rule in Phase 5. A wrong `copy` tells a reader to drop a message the
sender really sent, which is worse than an unmarked copy, so the rule errs
toward leaving it unset.

## Sequencing and risk

- **Phases 1 and 2 move no file byte.** `tools/byte_identity.py` against
  `v0.8.0` confirms it after each.
- **Phases 3–5 move bytes only for inputs no fixture has**, as far as #73's
  review found. Each confirms that against `v0.8.0` and names any exception.
- **The risk is a citation in the wrong place.** #74's blocks point into the
  capture file by byte offset, and an offset off by a record header would
  still read back clean. The vector's `[40, 106)` is the check.
