# Plan: the `v0.1.0` release

**Written 2026-09-07.** `0.1.0` is the **first tag** this project will carry.
Everything the tool does is already listed under `## [Unreleased]` in
[`CHANGELOG.md`](../CHANGELOG.md); what stands between that text and a tag is
the two open issues, and the release mechanics they gate.

Against the two issues open today:
[#11](https://github.com/adamkjonsson/python-zipline-wire/issues/11) and
[#13](https://github.com/adamkjonsson/python-zipline-wire/issues/13).

| Issue | What it really is | Blocking? |
| --- | --- | --- |
| #13 | The **port to python-zipline 0.3.0 / spec `0.19`** — three options gone, `record()` regrouped | **Yes.** The tree does not run against the installed sibling at all |
| #11 | A **fidelity bug**: a coalesced record's `ack` comes from no rule | Yes, in the sense that it changes what a `.zpf` says, and after a tag that is a break |

They are unequal in size. #13 is the release; #11 is a twenty-line fix with an
argument attached.

## Where the tree stands

Measured, not assumed. The venv installs both siblings editable from the
checkouts beside this one, and `../python-zipline` is now at **0.3.0**, so the
port has already happened underneath us:

```
$ .venv/bin/python -c "import zpf; print(zpf.SPEC_VERSION)"
(0, 19)

$ .venv/bin/pytest -q
228 failed, 44 passed
```

Nearly every failure is one line — `TypeError: create() got an unexpected
keyword argument 'single_clock'` at [`convert.py:142`](../src/zpfwire/convert.py#L142)
— reached through the `to_zpf` helper that every test goes through. The
`record()` signature change is behind it and will surface as the second wave.

**This is the `0.x` rule working, not a regression.** A `0.2.0` file is refused
by `0.3.0` at the version gate and vice versa; every spec minor is a separate
format. What it means for us is that there is no partial port: the tree writes
`0.16` today and will write `0.19` when Phase 0 lands, with nothing in between.

## What the port has to carry

From #13, verified against our own tree rather than taken on trust.

### Three options left the format

| Where | What | Do |
| --- | --- | --- |
| [`convert.py:142`](../src/zpfwire/convert.py#L142) | `single_clock=True` on `zpf.create()` | delete the argument **and the comment at `:139-141`** |
| [`convert.py:283`](../src/zpfwire/convert.py#L283) | `sequenced_basis="clock" if causal else None` | delete the argument **and the comment at `:276-283`** |
| — | `zpf.Origin`, `zpf.FileFlags`, `zpf.SEQUENCED_BASES` | we never used `Origin`; `FileFlags` is used **once, in a test** ([`test_convert.py:54`](../tests/test_convert.py#L54)) |

`SEQUENCED` survives and so does our reason for setting it. What went is the
obligation to *justify* it: a hint-less sequenced session no longer records a
basis, because a reader cannot check the basis any more than it can check the
order, so the producer is trusted for both. **The empty-session trap therefore
stops being a trap** — and it is documented in two places as the subtlest thing
in the writer, so this is a prose problem more than a code one. See Phase 0's
documentation sweep.

### Both `record()` call sites move

Twelve flat keywords became nine, grouped on the format's own transport/decoded
line. Three call sites, two shapes:

```python
# tcp.py:224 (_syn_record) and tcp.py:488 (_flush)
self.session.record(participant, ts=..., payload=..., flags=..., ts_first=...,
                    hints=zpf.Hints(seq_start=..., ack=...),
                    decoded=zpf.Decoded(decoder=self._decoder))

# udp.py:35 — no seq_start/ack, so only the decoder moves
self.session.record(sender, ts=..., payload=..., flags=RecordFlags.MESSAGE,
                    decoded=zpf.Decoded(decoder=self._decoder))
```

`zpf.Hints` moved from `zpf.decode` to `zpf.writer` and is exported as
`zpf.Hints` either way. `zpf.Decoded` is `decoder` + `content_type` + `role` +
`spans` — the options the layer rule governs. We set only `decoder`, and that
is the point: our records speak to the transport layer, and `Decoded` is where
the file's one decoded-layer statement goes.

`writer.undecoded()` is unchanged, so [`flow.py:156`](../src/zpfwire/flow.py#L156)
and the four `undecoded()` calls in `tcp.py` stand as written.

### Two things did **not** change, and both are ours

The upstream simplification analysis proposed five reductions; `0.19` took
three and declined two, and the two it declined are the two we depend on.

- **`output_layer=zpf.OutputLayer.TRANSPORT`** ([`convert.py:161`](../src/zpfwire/convert.py#L161))
  stays. Package E would have collapsed provenance and layer into one axis and
  taken the reassembler's `params_digest` with it — the only place our overlap
  and gap policy is recorded, which is what makes a conversion reproducible.
- **`reason_class`** ([`flow.py:165`](../src/zpfwire/flow.py#L165)) stays.
  Package D would have made coverage a SHOULD; the `0.18` re-issue added a Goals
  entry — *make a decoding failure findable in the input's own bytes* — that it
  would have contradicted. That goal is the whole reason our `Undecoded` blocks
  exist.

Worth recording in `PLAN.md`'s upstream ledger: **this project's declaring
itself a reassembler is part of why E was declined.**

### One thing already fixed, and one claim to correct

The below-origin SYN ([python-zipline#63](https://github.com/adamkjonsson/python-zipline/issues/63))
is fixed here already, in commit `7ee455c`, which is why the current branch is
named for it. `0.3.0`'s writer now **refuses** a `syn` record whose `seq_start`
is not `isn + 1`, and refuses a payload-carrying record below the origin — the
second being explicitly stricter than the format. Our output passes both,
verified upstream at their Phase 4. Phase 0 confirms it by running rather than
by reading.

**But #13 says "you already write the first two" of `produced_by`,
`produced_at` and `transform_params_digest`, and we do not.**
[`convert.py:138`](../src/zpfwire/convert.py#L138) writes `produced_by` and
nothing writes `produced_at`. That matters more under `0.19` than it did under
`0.16`, because build provenance is now *where the forensic answer went* when
the basis left the format. See Decision 1. A note goes back on the #13 thread
either way, correcting the record.

`transform_params_digest` is **not** ours and nobody should reach for it: it is
for a transform that produces records without decoding them. Our configuration
lives on the Decoder, which is what `create()`'s own docstring says a decode
stage does.

## Phase 1 — #11: give the coalesced `ack` a rule — **DONE** (2026-09-07)

Small, and the whole of it is deciding *which* rule. The bug is
[`tcp.py:299`](../src/zpfwire/tcp.py#L299):

```python
stream.run.ts = max(stream.run.ts, pkt.ts_ticks)
stream.run.ts_first = min(stream.run.ts_first, pkt.ts_ticks)
stream.run.ack = pkt.ack          # ← last append wins
```

The two stamps above it became per-unit extremes in `7ee455c`; the `ack` beside
them did not, so a record now reports a timestamp and an acknowledgement taken
from **two different packets**. A segment held out of order arrives before the
segment that fills the hole below it and is appended after it, so a drained run
keeps the *earlier* packet's ack.

**Take the serial-arithmetic maximum over the run's contributing packets**, the
shape the two lines above it already have. Acks are cumulative, so an ack
observed on any contributor is still true when the run completes; the
specification blesses folding a pure ACK's number into the next data record for
exactly this reason. The alternative — take the ack of the packet that supplies
`ts` — keeps the two hints on one packet but throws away a true edge whenever
the last contributor's ack is the lower one, which a delayed ack makes common.

Max is also the only one of the two that is *conservative rather than
arbitrary*: it can never overstate, because it never states an ack no
contributor sent.

- [x] [`tcp.py:299`](../src/zpfwire/tcp.py#L299):

  ```python
  if stream.run.ack is None or _delta(pkt.ack, stream.run.ack) > 0:
      stream.run.ack = pkt.ack
  ```

  `_delta` ([`:63`](../src/zpfwire/tcp.py#L63)) is the serial comparison already
  in the file. The `None` guard is load-bearing: `_Run.ack` starts unset.
- [x] The comment at [`:291-296`](../src/zpfwire/tcp.py#L291) explains the two
  stamps. Extend it to three, and say **which** rule and **why** — the issue
  asks for exactly this, and "nothing in the code or the docstrings claims this
  is intended" is half of what made the old behaviour a bug.
- [x] `_Run.ack`'s field comment at [`:100`](../src/zpfwire/tcp.py#L100) —
  it has none today; give it the one-line rule.
- [x] **Check the two synthesized `PacketView`s against the chosen rule**, as
  the issue asks. Both fold in through `_append` and so inherit the max:
  `_stamp` ([`:504`](../src/zpfwire/tcp.py#L504)) carries `ack=held.ack` for a
  drained segment, and `_commit_remaining` ([`:393`](../src/zpfwire/tcp.py#L393))
  builds one carrying the same. Confirm by running, and record that they need
  no change of their own — that is the payoff of putting the rule in `_append`.
- [x] `_syn_record` ([`:229`](../src/zpfwire/tcp.py#L229)) writes a
  single-packet record, so max over its contributors is that packet's ack and
  the code stands. Its `ACK`-flag gate stays, and Decision 2 makes that an
  asymmetry to **explain in the comment** rather than one to remove: an initial
  `SYN` has nothing to acknowledge, where a data segment always does.

### Tests

### Not a break, this once

A `.zpf` whose bytes move for the same input and the same options is normally a
break under [`CHANGELOG.md`](../CHANGELOG.md)'s versioning rule. **Nothing has
been released**, so this and Phase 0 both land as plain entries in the `0.1.0`
section with no `Breaking:` marker and nothing for anyone to migrate. It is the
last time that will be true, which is an argument for landing #11 now rather
than after the tag.

### What Phase 1 execution changed

- **Three of the four new tests fail under the old rule; the fourth passes, and
  that is the point of it.** The one that passes is the higher-ack-on-the-held-
  segment case, which the issue itself names as *sound by luck* — the old
  behaviour got it right for no reason. Keeping a test that both rules pass is
  worth it here: it is the test that says the maximum is a rule rather than a
  fix aimed at one trace. Verified by reverting the two-line change and running
  the four.
- **The wrap test earns its keep.** A plain `max()` on the two acks either side
  of 2³² picks the numerically larger and hands the record an ack four billion
  bytes in the past. `_delta` was already in the file for `seq`; nothing had
  ever exercised it on `ack`.
- **The `--sequenced` test asserts the ack, not just the order.** The plan
  asked for "the same conversation sequences identically with and without a
  reordered segment", and that assertion turns out not to discriminate: a
  linearization can arrive at the same order by other routes, so it would pass
  under either rule. What does discriminate is the number the merge consumes,
  so the test builds a run whose two segments carry different acks — the second
  stale, the peer's acks having been reordered — and asserts the record carries
  the higher one and is stored after the banner it acknowledges.
- **Nothing had to change in `_stamp` or `_commit_remaining`**, as the plan
  predicted: both fold their synthesized `PacketView` through `_append`, so
  putting the rule there covers them. Confirmed by running rather than by
  reading, which is the only way that claim is worth anything.

## Decisions taken

Three, settled 2026-09-07. Only the first changes what the tool writes.

### 1. Does a capture-sourced file write `produced_at`? — **Yes**

**Taken as recommended**, including the keyword: the file is stamped by
default, and a caller who needs byte-identical output pins the value.

The cost is accepted rather than dismissed — a wall-clock stamp does make every
conversion of one capture produce different bytes — and is to be **revisited in
a later version of the Zipline Payload Format**, which is where the question
belongs: build provenance having absorbed the forensic answer, the format is
what decides how a producer states it.

`0.19` moved the forensic answer that `sequenced_basis` used to give onto the
file's build provenance — `produced_by`, `produced_at`,
`transform_params_digest`. We write the first, not the second. A capture-sourced
file is not *derived*, so neither is required of us; but `produced_by` was set
on the same permitted-not-required footing, and "when was this built" is the
question a consumer asks of a `SEQUENCED` file now that nothing else answers it.

**The cost is real and worth stating: a wall-clock stamp makes every conversion
of the same capture produce different bytes.** That is not a conformance
problem, and the reproducibility this project actually claims is the *decode's*
— `params_digest` on the Decoder, which is unaffected. But byte-identical
output is a property some consumer will lean on, so:

- write `produced_at` by default, and
- expose it as a parameter on `capture_to_zpf` / `convert` so a caller who
  wants determinism can pin or omit it.

**The shape**, since `zpf.create()`'s own `None` already means *absent* and we
need three answers rather than two:

```python
produced_at: int | datetime.datetime | Literal["now"] | None = "now"
```

`"now"` stamps the conversion, an `int`/`datetime` pins it, and `None` omits
the field — `None` keeping the meaning it has downstream. It is an `Added`
entry and a row in [`docs/reference/zpf-mapping.md`](../docs/reference/zpf-mapping.md).

**No CLI flag.** `--produced-at` is not added: the CLI's job is conversion, and
a caller who needs a pinned stamp is scripting one, which is the API's job.
Recorded in [`docs/reference/limits.md`](../docs/reference/limits.md) so the
gap is stated rather than discovered — a conversion run from the command line
is not byte-reproducible, and that is the first thing to revisit alongside the
format question above.

### 2. Does an `ack` from a segment with no `ACK` flag count? — **Yes, it counts**

**Declined: no `TCP_ACK` gate.** `_append` goes on folding every contributor's
`ack` into the maximum, and
[`test_the_ack_hint_comes_from_the_wire`](../tests/test_tcp.py#L324) stands
unchanged.

The argument for gating was that RFC 793 leaves the field undefined when the
flag is clear, so folding it could overstate. The argument against, which wins:
a segment carrying data without `ACK` set is vanishingly rare on a real
connection — every segment after the handshake carries it — and the value in
the field of one that does is far more likely to be a real cumulative ack than
noise. Reading it is the *observation*, and this tool reports what the capture
holds.

**So `_syn_record`'s gate at [`tcp.py:229`](../src/zpfwire/tcp.py#L229) stays a
deliberate asymmetry rather than an inconsistency to fix**, and Phase 1 says so
in the code: the initial `SYN` of a connection genuinely has no acknowledgement
— there is nothing yet to acknowledge — where a data segment always does,
whatever its flags say. The two cases differ in fact, not in policy.

### 3. Does `PLAN.md` move into `plans/`? — **Yes**

**Taken**, and moved forward from Phase 3 into Phase 0's documentation sweep:
the same commit already updates every file that references it, so moving it
later would touch them twice.

`PLAN.md` is the design record of how this project was built — phases, upstream
issues, decisions taken — and it describes several worlds that no longer exist
(spec `0.16` throughout, packeteer versions since superseded). That is exactly
what python-zipline's `plans/` holds, under a README that says plainly: *they
are historical, not normative; where one disagrees with the code, the code is
right.* Moving it costs three reference updates
([`CLAUDE.md`](../CLAUDE.md), `docs/internals/`) and stops the next reader
treating a description of `0.16` as instructions.

`CLAUDE.md` currently calls it "the design and phasing this project is being
built to", present tense, and the phasing it describes is complete. So the move
is also an admission that the plan is finished — which it is, and which is what
tagging `0.1.0` means.

## Sequencing and risk

**Phase 0 first, and not by preference — nothing runs until it lands.** With
228 of 272 tests failing on `create()`, the suite cannot tell anyone whether
Phase 1 is correct. Do the port, get green, then change behaviour.

**Phase 1 second, and before the tag.** It moves bytes for the same input,
which after a tag is a documented break requiring a `Breaking:` note and a
migration line. Before the tag it is one entry under `Fixed` with nothing owed
to anyone. Landing it after `0.1.0` would cost more than the fix.

**Phases 2 and 3 are mechanical** and carry one risk between them: the release
names three version numbers, and getting one wrong is the kind of error nothing
catches. `zpf.SPEC_VERSION` is the source of truth for the spec number and the
new pyproject-URL test pins it; the two sibling versions are transcribed by
hand from their tags.

**The one thing that could surprise us** is a `0.19` rule our output breaks that
neither #13 nor upstream's own Phase 4 anticipated — most plausibly through
`FileReader.unplaceable`, which did not exist when any of our files were last
read back. That is why the new assertion is in Phase 0's tests rather than
listed as a nice-to-have: it is the phase's own regression guard, and if
something is wrong it will be wrong there.
